# Agent Note: 精选插件层治理

Status: implemented

[English](2026-08-25-curated-plugin-layer-governance.md) | 中文

## Problem

Profile 组合包让树外插件可以被安装，但它们不回答产品认可哪些第三方插件、哪些事实经过 audit、哪些组合被允许，以及被拒绝候选如何留在可运行 profile 之外。如果没有仓库持有的治理层，每个精选 profile 都会把信任决策编码进临时组合包列表，audit 失败的候选也可能作为占位依赖漂进 active profile。

## Decision

`packages/curated/` 是仓库持有的精选第三方插件组合与准入层。它在现有 profile 组合包系统旁边增加包，而不修改 `packages/core/agent-loop`、会话协议格式（wire format），或已交付的 `web` 和 `headless` profile 模板。这五个 curated 包都是 DSH 发布族的公开成员，因为 `@deepseek-ai/dsh` 会安装 `curated-base` 与 `curated-profiles`，这两个包需要 `curated-policy` 与 `curated-bench`，而 `curated-scripts` 会向用户提供命令。发布规划器会先发布每个安装依赖，再发布其消费方。[profile 插件组合包决策](2026-08-05-profile-plugin-bundles.zh.md)继续拥有 profile manifest 如何解析并应用组合包层；精选层拥有哪些候选事实被接受进新的 `web-curated`、`web-coding`、`web-research`、`web-enterprise` 和 `web-personal` 模板。

`@deepseek-ai/dsh-curated-base` 是静态组合包，其 patch 插入 `@deepseek-ai/dsh-curated-policy` 和 `@deepseek-ai/dsh-curated-bench`。`@deepseek-ai/dsh-curated-policy` 持有固定 allowlist、计算得到的八维准入分类、权威 provider/fallback 规则、重复资源检查、secret 拒绝与脱敏，以及只读 `ctx.curatedPolicy` 服务。Active 候选必须具有已验证 Node 证据，并且不得修改 Harness core 路径。`@deepseek-ai/dsh-curated-profiles` 持有确定性的精选 profile 模板，将其物化到指定 DSH home，同时不覆盖已有文件，并为启动器提供强制组合准入。`web-curated` 的目标基线包含 12 个候选。Web 搜索、memento、MCP panel、检查点回退、LSP 操作和 LoongSuite 遥测是静态/安装资格候选，但都没有基于其固定产物的 keyless assembled runnable snapshot，因此 runtime active 数为 0。Web 搜索还缺少必需的 `@anweat/dsh-browser` bundle/runtime dependency。五个精选模板都只包含三个安装自有基础 bundle。每个 selected active candidate（包括声明必需 runtime bundle 的 consumer）都携带 `runtimeActivationEvidence`，其 key 必须与 `targetProfiles` 精确一致；每个 profile 值都把 keyless assembled snapshot 以及安装、启用、重启、禁用或卸载记录绑定到该 profile、安全仓库相对路径和非占位 SHA-256，其中的必需 bundle 列表必须匹配候选声明。Curated policy 持有这些规则唯一的当前 profile 完整性谓词；详细 validator 与 profile dependency 物化都使用该谓词的检查。Catalog policy 失败时，仓库文档与 DSH release 门禁会在访问 evidence 前仅返回已脱敏的 policy diagnostics；否则会解析每个 profile 的记录，要求预期 lifecycle 操作和成功 observed 命令结果，绑定候选、profile key、当前模板与 active 组合摘要、源码、安装目录、runtime closure 与必需 bundle identity，通过有界稳定 descriptor 读取校验每个独立引用产物，并重放精确的 Git tracked candidate/profile/operation snapshot 测试。公开 activation diagnostics 会脱敏 secret-like candidate、profile 与 path 标识。该产物会重复这些 identity 与 operation，并携带匹配且不含 secret 的 command、零退出码和 observed 成功结果。Record 与 artifact command 会拒绝 Authorization、Bearer、`sk-*`、GitHub token，以及非空的 secret、token、password、key 或 cookie 形态 option，包括 URL userinfo 与 secret query 参数，且诊断不包含 argv；含有 `token-meter` 等单词的普通路径仍然合法。每份 keyless assembled 记录与产物还要求已验证 waterfall 委托，以及重复 token 注入或外部请求均为 0，因此只删除 rejection 并设置 `active: true` 无法激活候选。每个必需 runtime bundle 都由同一 profile 中另一个具有 activation evidence 的 active 候选提供；两个候选都会进入 profile dependencies，observed 解析还要求 manifest、root lock、installed lock 与已安装包目录中都存在各自依赖。`@deepseek-ai/dsh-curated-bench` 持有 benchmark 定义、计划记录或调用方提供的记录，以及只读 `ctx.curatedBench` 查询服务；它不执行 A/B 工作负载。`dsh` 启动器只会在配置 dump 或 Loader 激活前，为这五个精选 profile 名称调用物化器和准入；已交付的 `web` 与 `headless` 初始化仍由 app-boot 持有。精选准入要求模板与 catalog 的 bundle 顺序精确一致、包管理器设置安全、组合包保持 installation-first 解析，并且用户静态覆盖不得包含动态表达式或插入 plugin/group。已有精选 `.npmrc` 仅在其字节与生成的 `ignore-scripts=true` 文件完全一致时才会被接受。精选插件管理只允许帮助、列表查询，以及在禁用生命周期脚本时不带额外参数地安装模板声明依赖。帮助与列表由签入模板数据生成，不创建 profile 状态也不调用 pnpm。Bare install 会持有跨进程 profile writer lock，恢复或删除中断的激活与 staging 状态，创建私有 staging home，保留通过校验的已有 profile patch 与 lockfile，只使用本地 pnpm store，冻结该已有 lockfile，移除 ambient npm/pnpm config，把 pnpm 的 user/global config 固定到 staged profile `.npmrc`，并拒绝根目录重定向、包变换或构建授权环境注入；本地缺包时安装失败，不会发起网络抓取。激活前，它会保留并检查 staged 受管文件与两份 lockfile，解析完整 bundle 栈并执行精选准入。pnpm 或校验失败会保持旧 live 目录不变；激活失败会恢复旧目录。只有在 writer lock 仍然持有时，staged 目录才会通过目录 rename 变为 live。精选 profile 与 `profiles` 根必须保持为 DSH home 内的普通 canonical 目录，启动会在修复共享 module fallback 前校验该包含关系；add、remove、带参数的 install 和其它 package-state 命令会破坏固定组合，因此在运行 pnpm 前被拒绝。`@deepseek-ai/dsh-curated-scripts` 持有更深层的本地 `verify-lock`、`preflight`、`smoke-profile` 和 `compare-benchmark` 命令实现。每个已发布命令都有独立可执行模块，并共用同一个 runner，因此 package-manager shim 无需从共享模块文件名推断命令。

Profile 物化器会在宿主支持时使用 `O_NOFOLLOW` 打开已有的 `package.json`、`cordis.patch.yml`、`pnpm-workspace.yaml` 和 `.npmrc` 文件，要求 `lstat` 与 `fstat` 的非零 device/inode identity 一致，从同一 descriptor 读取并校验字节，并在读取前后核对 descriptor、文件路径与 profile 目录 identity。它使用这份短生命周期 descriptor 快照校验已有文件，并在物化完成时将其关闭。物化后，精选 CLI 会打开一份新的 retained snapshot；该快照的 profile 与 `profiles` 目录 identity 会独立重新绑定到同一个 DSH home 包含关系，并跨通用 profile 加载与准入保持打开。每次 live HMR 重组都会打开一份新快照、复核其 identity、从其字节解析 profile patch、使用该快照执行准入，并在 `finally` 中将其关闭。Boot 后的 timer、HMR、profile watch 与 home watch setup 构成一个事务：部分失败会逆序释放已完成的注册并等待 root disposal；app 请求退出时，只会在 cleanup 达到 quiescence 后抑制 setup 错误，cleanup 错误仍会报告。因此受管文件或 profile 目录祖先被替换时会 fail-closed，且不会读取外部 symlink 目标。纯 Node 路径 API 不能阻止具有相同文件系统权限的攻击者执行每一次瞬时目录替换，该机制不作更广泛保证。Symlink、junction 和非普通文件会被拒绝；缺失文件使用排他创建。精选 manifest 会在包管理器执行前拒绝整个 `pnpm` 字段，包括 `pnpm.configDependencies`。公开 activation diagnostics 使用 policy redactor 遮蔽 key/value secret、Authorization 值，以及带 scheme URL 的 authority 中直到最后一个 `@` 的完整 userinfo；之后 path、query 或 fragment 中的 `@` 保持可见。Command 检查只在 secret key/value 或 header 语境中把 `authorization` 视为 secret，因此仓库生成的 snapshot path 与测试名称可以包含该普通单词，而真实 Authorization header 仍会被拒绝。

缺失的受管文件会在目录 snapshot 保持打开时，通过已校验 descriptor 写入随机临时文件，再以排他 hard link 发布。每次成功发布都会被纳入该 snapshot；后续失败时，只要 identity 未变化，物化器就按逆序删除同一次调用创建的文件。并发发布只有在 retained 字节与生成字节相同时才会被接纳。把 profile 祖先替换为指向无关外部目标的 symlink 或 junction 不会让该目标接收受管字节或出现受管文件名，操作会 fail-closed。Node 没有与 `openat`、`linkat` 和 `unlinkat` 等价的跨平台 descriptor 相对 API。在最后一次目录 identity 检查与路径式 `linkSync` 之间，具有相同文件系统权限的进程可以把已经打开的原目录移出 DSH home，再让原路径指回该 inode；此时 `linkSync` 可能先在移动后的原目录中把完整临时文件发布为受管文件名，随后的 identity 检查才会 fail-closed。物化期间，调用方必须排他管理 DSH home。临时 descriptor 始终会被关闭。如果首次 identity 获取失败，cleanup 会在不尝试 identity-based unlink 的情况下删除仍可达的随机路径；取得 identity 后，cleanup 会在 `unlink` 前校验该 identity。移动后的原目录中可能留下不可达的随机临时文件，且 identity 检查加 `unlink` 不构成针对同权限替换的原子 compare-and-unlink。公开 activation 诊断会遮蔽 DNS 名称或带方括号 IPv6 literal 的无 scheme `user:pass@host:port` userinfo，同时保留普通 `@` 文本。

`curated-policy` 和 `curated-profiles` invariant companion 注册带说明的空 installer。其固定 catalog 与模板没有事件流或可变数据关系；策略插件加载、聚焦包测试和 `verify-curated-activation-evidence` 保留静态校验。

[精选 benchmark 证据目录](../../../../packages/curated/curated-bench/evidence/README.zh.md)持有激活记录及其结果产物。每份记录和引用产物都是该目录中唯一、由仓库持有、已跟踪且处于 stage zero 的普通 blob；每份 JSON 记录遵循 operation schema，并通过 SHA-256 绑定独立结果产物。包自身提供、ignored 和 untracked 的文件不能授权激活。

allowlist 按稳定 id、能力、无凭证的 canonical GitHub 仓库 URL、完整 commit SHA、包元数据、许可证、组合包 patch、网络与凭据声明、安装生命周期脚本、目标 profile、active 标记、警告、blocker，以及总和构成准入分数的八个受限评分维度记录每个候选。策略不存储另一份 status 字段，而是推导 `active`、`qualified`、`pending` 或 `rejected`：active 候选优先；安装 metadata 与产物摘要完整、且 blocker 只表示缺少激活证据的候选为 qualified；long-cycle 或 baseline-promotion blocker 对应 pending；其它 blocker 对应 rejected。每个 inactive 候选都至少有一条 blocker，因此 inactive fallback 的意图不能只存在于 prose 中。每个可达源码都记录 `sourceContentSha256`。`pnpm run audit-curated-candidates -- --candidate <id>` 会将固定 commit 抓取到临时 bare Git 仓库，并且不创建 checkout。摘要以 `dsh-source-content-v1\0` 开头，按 UTF-8 POSIX 相对路径字节对条目全局排序，再依次哈希带长度前缀的 entry mode、对象类型、路径和 blob 字节。Symlink 会贡献其 `120000` mode 和链接目标 blob，但不会被跟随；不支持的 mode 和非 blob 条目会被拒绝。该摘要标识固定 Git tree，不受 GitHub 可变 source archive 编码影响。候选还可以在保留仓库与 commit audit 的同时固定精确 npm 版本和 registry integrity。每个 active 候选都固定其已审计安装目录与完整 runtime 依赖 lock 闭包的 SHA-256。安装目录摘要使用自身的有序路径与内容编码，因此新增、删除或修改直接候选文件都会被拒绝；闭包摘要按 package identity 与确切 registry SRI 或不可变 Git identity 排序。pnpm v9 alias 通过真实目标的 package 与 snapshot 记录解析，其 identity 同时绑定声明别名与真实目标；普通依赖 identity 保持原表示。Active Git 依赖不得声明 `preinstall`、`install`、`postinstall`、`prepare` 或 `prepack`；它必须使用经过验证的预构建 npm 产物，否则保持 inactive。只校验 catalog 会检查这些声明内部是否一致，不会抓取或证明上游产物。对于物化后的 profile，observed lock 校验、preflight 与 smoke 从 profile 依赖 spec、根 pnpm lockfile 和 pnpm 的已安装 lock 快照派生来源。Git 候选必须与 catalog 的仓库、commit、路径、包版本和目录摘要一致；npm 候选必须与确切版本、integrity 和目录摘要一致。普通 peer 后缀仍然有效，但 root/workspace `overrides`、`patch_hash` 后缀、`patchedDependencies`、`packageExtensions` 和 pnpmfile 变换会被拒绝，因为改写后的依赖内容没有独立 catalog pin。两份 lockfile 必须描述通过 `dependencies` 与 `optionalDependencies` 可达的同一个完整 runtime 闭包：每个 registry 依赖都具有确切版本与 SRI，每个 direct Git locator 都精确匹配解析得到的 repository、完整 commit 和 package path，每个 GitHub tarball 都按 commit 寻址；两份计算出的闭包摘要还必须匹配 catalog，因此攻击者同时修改两份 lockfile 仍会被拒绝。pnpm 会在安装时校验 registry 归档 integrity。Observed 准入会校验这些依赖 lock 来源并检测直接候选目录篡改；它不声称能够检测同时保持两份 lockfile 不变而直接改写任意传递依赖文件的攻击者。命令要求每个规范化后的选中包根目录位于 profile 的规范化 `node_modules` 根目录下，并在访问前规范化每个 manifest、bundle patch 与 main 路径。Windows drive、UNC、反斜杠、遍历、symlink 和 junction 逃逸会在所有宿主上失败。在宿主支持时，文件会以 no-follow 方式打开，在有界 descriptor 读取前后使用 `fstat()` 校验，再对照 package 相对路径与普通祖先复核已打开 identity；非普通文件、路径或祖先被替换、读取期间变化、单文件超过 16 MiB 或使直接候选目录超过 64 MiB 都会失败。命令随后校验已安装 manifest、组合包 patch、声明的 main 文件、依赖、lifecycle hook、Node 范围和候选专属安全设置，并且不运行包脚本。候选 bundle patch 使用 Loader 的 `entryListSchema`；每个插入层级和 group 层级中的非法 mapping 行都会失败。完成 Cordis 组合后，每个顶层有效行和嵌套 group 有效行都必须带有非空字符串 `id` 与 `name` 字段，而且每个 truthy group 都必须包含条目列表形式的 `config`，随后才会将候选 entry ID 与 catalog 比较。Observed preflight 会组合候选 bundle、profile、Harness home 和显式 overlay patch。每个插件与 group 行都必须保留已批准所选 catalog 候选或安装自带 bundle 的所有权，无论其 `disabled` 值为何；Cordis 即使看到字面量 `disabled: true` 也会导入 group。用户控制的 profile、home 与显式 overlay patch 会在 Loader 解析前拒绝 `!!js`，包括对获批行 name、config 和 `disabled` 的覆盖；已批准 catalog 与安装 bundle patch 可以保留经过 audit 的表达式。Permission provider 仍采用更严格要求：其配置项及每个祖先 group 必须省略 `disabled` 或将其设为字面量 `false`。已批准插件行在保留 ID 与模块名称时可以被静态覆盖，用户控制的插件和 group 插入会 fail-closed。Preflight 对同一递归条目集合执行来源所有权以及冲突、资源与 secret 检查。缺失、浮动、过期、非法、经过变换或不匹配的包管理器状态会 fail-closed。没有受管 profile 的显式产物根只校验 metadata，永远不会建立 observed 成功；包自身提供的伴随文件不是准入证据。Smoke 会在可终止 worker 中执行 observed 产物与包管理器 staging，再在同一个执行工作期限内调用已交付 CLI 的 `--dump-config` 和 `--help` 阶段。Worker 返回结果、报错或超时后，命令都会先释放其计时器、listener 和事件循环引用，再发起终止，并等待 worker 退出后才返回。Worker 构造与终止清理属于工作预算之外的不可抢占开销，因此命令不承诺硬性总 wall-clock 上限。Production observed smoke 会把通过校验的 profile 与可选 Harness-home patch 复制到私有 execution home，重新校验该副本，并从中启动两个 CLI stage，因此随后修改所提供的 live 路径无法改变 child 输入。Smoke 不导入候选模块，也不合成 bundle shim。Metadata 与配置 secret 检查覆盖 curated 字段；非法 YAML 诊断保留 parser 位置、caret 和非秘密 code-frame 行，但不附加仍持有原始源码的 parser exception，同时由 escape-aware 键解析遮盖完整 secret scalar continuation。非 JSON 诊断会删除 secret-shaped 赋值键后的整条物理行剩余内容，包括任意 Authorization scheme 和多词值，同时保留键及之前的非秘密上下文。Smoke 子进程会在合并 ambient 与显式环境后，以大小写不敏感方式删除名称包含 `KEY`、`PASSWORD`、`SECRET`、`TOKEN`、`AUTH`、`CREDENTIAL` 或 `COOKIE` 的变量；带 userinfo 的 proxy URL 也会被删除，返回的每个输出流都会遮蔽 URL userinfo，超时的 detached process tree 则依次收到 TERM 和 KILL，runner 会等待进程树静止后才删除临时目录。来源不可访问、许可证不清、缺包元数据、缺组合包 patch、Node 元数据不兼容、要求修改 core、缺少所需安全控制、需要额外威胁模型，或带有其他硬拒绝的候选保持 inactive，并且不进入 active profile 模板。当 inactive fallback 候选的 audit 记录仍能说明为什么某个 profile 里只有一个提供方拥有一项能力时，它可以留在 allowlist 中。

没有第三方候选 active 时，物化后的 profile patch 为空。候选专属安全设置继续保留在 catalog 中，供后续准入使用。每个精选 profile 都写入 `ignore-scripts=true`，生成的 workspace 不含构建授权或包变换，已有不安全文件会在任何写入前导致拒绝。对精确生成的 curated manifest 进行 observed 校验时，必须确认 `private: true`、生成的 dependency 名称集合、不含额外 dependency 区段，并且即使该集合为空也同时存在根与已安装 pnpm lockfile。CLI 还会为每次插件管理操作同时强制 pnpm 的脚本禁用配置和环境变量。Preflight 会在组合前扫描每个原始 profile、Harness home 与显式 overlay patch 中的 secret，包括会被组合丢弃的 target-only patch。Preflight 会解析 config-only override，但不会将其与官方 `--dump-config` 基线比较，因此替换字段的完整性由操作者审查。`verify-lock` 使用独立计数报告 catalog metadata 和选中进行观测校验的产物，并明确标注来源范围。Benchmark schema 3 比较要求任务与 attempt 集、critical 标记、环境、DSH build identity 与 measurement identity 完全一致，每项任务至少重复 5 次，以避免有限输入求和溢出的方式计算有限均值，以原始值判定阈值，并使用经过摘要校验的内嵌 lock 和 profile snapshot。Build identity 记录 DSH 包版本、完整源码 revision、源码树摘要、dirty 状态、可执行产物摘要和 Node 版本；measurement identity 记录 producer、tokenizer、prompt/schema 序列化、计时、定价与评分实现。每个 lock 或 profile 引用只包含相对于 benchmark fixture 目录的安全 JSON 路径与 snapshot canonical JSON SHA-256。其 canonical 路径必须留在该目录内，普通文件读取有大小上限，并且必须在语义校验前匹配摘要。Baseline 引用内容必须与内嵌 snapshot 的 canonical 内容完全相等；每个 profile snapshot 还必须精确匹配对应的 shipped 或 curated 权威模板，随后才能返回 rollback 数据。已完成的 JSON 输出会保留按内容寻址的引用与 execution identity。比较器返回决策、原因和不可变 rollback 内容；外部 rollout operator 负责恢复，不声称自动或原子恢复。没有 run 的 planned 记录可以省略 execution identity。`evidenceKind: observed`、producer metadata 和运行字段仍是 operator 所信任的断言：该标签与 `accepted` 结果都不会以密码学方式认证 producer 或 evidence。E3/E4、A/B、故障与 canary 证据均为 pending。

回滚 lock snapshot 将每个 candidate 编码为共享 artifact identity 加一个安装来源。Registry 来源携带确切 npm 版本与 SHA-512 SRI；Git 来源携带 normalized HTTPS repository、完整 commit、显式 repository path 与空 lifecycle-script 记录。静态校验会遍历 lock 与 profile 目录中的每个已发布 JSON 文件，要求 schema version 为 2、kind 与目录一致、profile 非空、payload 完整，并对每个 lock candidate 执行确切安装来源校验。Snapshot 文件读取只打开目录内的 canonical target，并要求其非零 device/inode identity 在读取前后都与已打开 descriptor 及 open 后路径检查一致。仅包含第一方 bundle 的 baseline 仍可使用空 candidate 数组。

无法重建 schema 2 lock 或 profile 的规划 metadata 位于 `baselines/history`，使用递归校验的 schema 1 `curated-planning-history` 记录，并明确标记 `evidenceKind: planned` 与 `restorable: false`。每条记录通过 migration map 保留原 lock/profile 路径、kind、operator 指令、数量、catalog 引用和 profile bundle。比较器只接受 schema 2 回滚 snapshot，因此 history 可以保留，但不会成为恢复输入。

Benchmark run 在成功时要求 `failure: null`，失败时要求非空原因。Failure distribution 通过 `Map` 统计每个失败 run，包括 property-like 名称，并按 locale 顺序输出 key。

Smoke 执行工作预算从函数入口开始计时。JavaScript 无法抢占同步 `Worker` 构造；构造返回后，命令才计入其已耗时间，若预算已耗尽则立即失败。Worker 检查与子进程阶段仍可终止。生产 child runner 接收剩余预算，public command 会等待其完成进程树与临时目录清理；injected runner 是可信测试控制，必须遵守传入 timeout，并仅在自己的清理完成后 settle。每条结果路径都会先清理 timer 与 listener，再等待终止。捕获的 stdout 与 stderr 共享 1 MiB 上限；输出超限会沿用 timeout 终止流程并返回有界诊断。Proxy 过滤会以大小写不敏感方式识别 conventional 与 npm-config 名称，删除带 userinfo 的 URL，并保留非 URL bypass 列表。构造超时与终止清理可能延长总 wall-clock；需要硬性操作系统截止时间的调用方负责监督 CLI 进程。

## Alternatives considered

**把精选行为放进 `agent-loop` 或另一个 core 包。** 不采用，因为精选准入是组合策略。core loop 已经接收组装后的插件树，不应理解第三方来源、许可证、安装脚本或 profile 分层规则。

**直接扩展已交付的 `web` 和 `headless` 模板。** 不采用，因为精选 profile 是 opt-in 组合。官方模板保持稳定基线，而精选模板可以承载更高的供应链与 profile 场景风险，并且不改变现有启动行为。

**在 audit 期间运行第三方安装或构建脚本。** 不采用，因为安装生命周期代码本身就是被评估的事实之一。仓库记录这些脚本，并在不执行它们的情况下校验元数据；profile 安装仍是精选准入检查之外的显式包管理器操作。

**从固定 Git commit 安装 LoongSuite。** 不采用，因为 Git 产物声明 `prepack: pnpm run build`。确切 npm `0.1.1` 包含已编译入口与匹配的 bundle patch，没有安装期脚本，其发布 tag 指向固定 commit，因此全部精选 profile 都使用该产物且不授予构建权限。

**信任包自身提供的来源伴随文件。** 不采用，因为被修改的包可以把预期仓库、commit 与源码内容字段复制进自己的伴随文件。受管 profile 使用 pnpm 的正常 lock 状态，而每条 observed 路径都会把已安装字节与独立维护的 catalog 目录摘要比较。

**每次启动都运行完整 observed preflight。** 不采用，因为 `curated-scripts` 已依赖 CLI 与 profile 包，从启动器反向导入会产生发布依赖环，并让启动执行产物目录与 lockfile 深检。Profile 包持有最小强制组合准入；observed preflight 继续作为显式的更深产物与 lock 校验。

**把失败候选作为 disabled 占位放进 active profile。** 不采用，因为可运行 profile 不应依赖 audit 失败的候选。拒绝原因留在 allowlist 中可见，但 active profile 路径只包含其场景已接受的提供方。

**把第三方插件 vendor 或 fork 进本仓库。** 不采用，因为精选层是治理与组合层，不是源码镜像。完整接收源码会让本仓库负责每个候选的构建、测试和依赖更新。

**让 curated 包保持私有，或把它们打进 CLI。** 不采用，因为已发布的 CLI 会在运行时按 npm 包标识解析组合包与 profile 包。只存在于 workspace 的私有依赖会使已安装 CLI 的依赖图无法解析；打进 CLI 则会替换既有的动态包加载模型，而且仍无法发布面向用户的 curated 命令。

## Consequences

精选 profile 文件可以从签入声明和确定性模板复现，而现有 `web` 与 `headless` 用户在选择精选 profile 之前保持相同组合。DSH 发布会打包全部五个 curated 包，并在发布前验证其导出文件和安装依赖图。文件可复现不代表第三方包可安装或运行时行为已经得到证明。模型本身不会看到 curated 包的治理文本；只有 profile 实际加载的组合包才会带来模型可见的提示词段、工具或结果。

audit 快照有意保持保守。候选可以有用但仍因当前证据不足而保持 inactive。外部安装与初始化、Chrome 浏览器回归、真实搜索、记忆、浏览器与 MCP A/B 工作负载、真实候选故障注入和 3–7 天 canary 证据仍待取得，不能由 fixture 或计划记录代替。

本决策不归档任何 active Agent Note。profile 组合包 note 仍拥有组合包解析与启动器行为，repository-plugin removal note 仍拥有避免第二条外部插件分发路径的决策。
