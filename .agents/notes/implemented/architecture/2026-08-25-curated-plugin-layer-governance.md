# Agent Note: Curated plugin layer governance

Status: implemented

English | [中文](2026-08-25-curated-plugin-layer-governance.zh.md)

## Problem

Profile bundles make out-of-tree plugins installable, but they do not answer which third-party plugins the product endorses, which facts were audited, which combinations are allowed, or how a rejected candidate stays out of a runnable profile. Without a repository-owned governance layer, each curated profile would encode trust decisions in ad hoc bundle lists, and a failed audit could still drift into an active profile as a placeholder dependency.

## Decision

`packages/curated/` is the repository-owned composition and admission layer for selected third-party plugins. It adds packages beside the existing profile-bundle system rather than changing `packages/core/agent-loop`, the session wire format, or the shipped `web` and `headless` profile templates. The five curated packages are public DSH release members because `@deepseek-ai/dsh` installs `curated-base` and `curated-profiles`, those packages require `curated-policy` and `curated-bench`, and `curated-scripts` exposes commands to users. The release planner publishes each installed dependency before its consumer. The [profile plugin bundles decision](2026-08-05-profile-plugin-bundles.md) continues to own how profile manifests resolve and apply bundle layers; the curated layer owns which candidate facts are accepted into the new `web-curated`, `web-coding`, `web-research`, `web-enterprise`, and `web-personal` templates.

`@deepseek-ai/dsh-curated-base` is a static bundle whose patch inserts `@deepseek-ai/dsh-curated-policy` and `@deepseek-ai/dsh-curated-bench`. `@deepseek-ai/dsh-curated-policy` owns the pinned allowlist, computed eight-dimension admission classification, authoritative provider/fallback rules, duplicate-resource checks, secret rejection and redaction, and the read-only `ctx.curatedPolicy` service. Active candidates require verified Node evidence and must not patch Harness core paths. `@deepseek-ai/dsh-curated-profiles` owns deterministic curated profile templates, materializes them into a requested DSH home without overwriting existing files, and supplies the launcher's mandatory composition admission. The intended `web-curated` baseline has 12 candidates. Web search, memento, MCP panel, checkpoint rewind, LSP actions, and LoongSuite telemetry are static/install qualification candidates, but none has a keyless assembled runnable snapshot of its pinned artifact, so the runtime-active count is zero. Web search also lacks its required `@anweat/dsh-browser` bundle/runtime dependency. All five curated templates contain only the three installation-owned foundation bundles. Every selected active candidate, including a consumer that declares a required runtime bundle, carries `runtimeActivationEvidence` whose keys exactly match `targetProfiles`; every profile value binds a keyless assembled snapshot and install, enable, restart, and disable-or-uninstall records to that profile, safe repository-relative paths, and non-placeholder SHA-256 values, and its required bundle list matches the candidate declaration. Curated policy owns one current-profile completeness predicate for these rules; its detailed validator and profile dependency materialization both use that predicate's checks. The repository documentation and DSH release gates return only redacted policy diagnostics without accessing evidence when catalog policy fails. Otherwise they parse every profile's records, require the expected lifecycle operation and successful observed command result, bind the candidate, profile key, current template and active-composition digest, source, installed-tree, runtime-closure and required-bundle identities, verify each separately referenced artifact through a bounded stable descriptor read, and replay the exact Git-tracked candidate/profile/operation snapshot test. Public activation diagnostics redact secret-like candidate, profile, and path identifiers. That artifact repeats the identities and operation and carries the matching secret-free command, zero exit code, and observed success result. Record and artifact commands reject Authorization, Bearer, `sk-*`, GitHub tokens, and non-empty secret-, token-, password-, key-, or cookie-shaped options, including URL userinfo and secret query parameters, without including argv in diagnostics; ordinary paths containing words such as `token-meter` remain valid. Every keyless assembled record and artifact also requires verified waterfall delegation and zero duplicate token injection or external requests, so deleting rejection evidence and setting `active: true` cannot activate a candidate. Every required runtime bundle is provided by another active candidate with activation evidence in the same profile; both candidates enter profile dependencies, and observed resolution requires each in the manifest, root lock, installed lock, and installed package tree. `@deepseek-ai/dsh-curated-bench` owns benchmark definitions and planned or supplied records plus the read-only `ctx.curatedBench` query service; it does not execute A/B workloads. The `dsh` launcher calls the profile materializer and admission only for the five curated profile names before config dump or Loader activation; shipped `web` and `headless` initialization stays owned by app-boot. Curated admission requires exact template and catalog bundle order, safe package-manager settings, installation-first bundle resolution, and static user overrides that do not contain dynamic expressions or insert plugins or groups. An existing curated `.npmrc` is accepted only when its bytes equal the generated `ignore-scripts=true` file. Curated plugin management permits only help, listing, and a bare install of the template-declared dependencies with lifecycle scripts disabled. Help and listing are generated from checked-in template data without creating profile state or invoking pnpm. Bare install holds a cross-process profile writer lock, restores or removes interrupted activation and staging state, creates a private staging home, retains a validated existing profile patch and lockfile, uses only the local pnpm store, freezes that existing lockfile, removes ambient npm/pnpm config, pins pnpm's user and global config to the staged profile `.npmrc`, and rejects root redirects, transformation or build-grant environment overrides; a missing local package fails instead of triggering a network fetch. Before activation it retains and checks the staged managed files and both lockfiles, resolves the complete bundle stack, and applies curated admission. pnpm or validation failure leaves the old live directory unchanged; activation failure restores it. The staged directory becomes live only through a directory rename while the writer lock remains held. Curated profile and `profiles` roots must remain ordinary canonical directories inside the DSH home, and launch validates that containment before healing the shared module fallback; add, remove, install arguments, and other package-state commands would violate the fixed composition and reject before pnpm runs. `@deepseek-ai/dsh-curated-scripts` owns the deeper local `verify-lock`, `preflight`, `smoke-profile`, and `compare-benchmark` command implementations. Each published command has its own executable module over one shared runner, so package-manager shims never infer a command from the shared module's filename.

The profile materializer opens existing `package.json`, `cordis.patch.yml`, `pnpm-workspace.yaml`, and `.npmrc` files with `O_NOFOLLOW` where available, requires matching nonzero device/inode identities across `lstat` and `fstat`, reads and validates bytes from the same descriptor, and checks descriptor, file path, and profile-directory identity before and after the read. It uses this short-lived descriptor snapshot to validate existing files and closes it when materialization finishes. After materialization, the curated CLI opens a new retained snapshot whose profile and `profiles` directory identities are independently rebound to the same DSH home containment; it retains that snapshot across generic profile loading and admission. Every live HMR recomposition opens a fresh snapshot, rechecks its identities, parses the profile patch from its bytes, performs admission with that snapshot, and closes it in `finally`. Post-boot timer, HMR, profile-watch, and home-watch setup is one transaction: a partial failure reverse-disposes completed registrations and awaits root disposal; an app-requested exit suppresses only the setup error after that cleanup reaches quiescence, while cleanup failures remain reported. A managed-file or profile-directory ancestor replacement therefore fails closed without reading an external symlink target. Pure Node path APIs do not prevent every instantaneous directory replacement by an attacker with the same filesystem privileges, and this mechanism makes no broader claim. Symlinks, junctions, and non-regular files reject; missing files use exclusive creation. A curated manifest rejects the entire `pnpm` field, including `pnpm.configDependencies`, before package-manager execution. Public activation diagnostics use the policy redactor for key/value secrets, Authorization values, and scheme URL authority userinfo through its last `@`; `@` in the following path, query, or fragment remains visible. Command checks require a secret key/value or header context for `authorization`, so repository-generated snapshot paths and test names may contain that ordinary word while real Authorization headers still reject.

Missing managed files are written to random temporary files through checked descriptors while the directory snapshot remains open, then published by exclusive hard link. Every successful publication is retained in that snapshot, and a later failure removes files created by the same materialization call in reverse order when their identities remain unchanged. A concurrent publisher is accepted only when the retained bytes equal the generated bytes. Replacing a profile ancestor with a symlink or junction to an unrelated external target does not send managed bytes or publish managed filenames into that target, and the operation fails closed. Node exposes no cross-platform descriptor-relative equivalents of `openat`, `linkat`, and `unlinkat`. Between the final directory identity check and path-based `linkSync`, a process with the same filesystem permissions can move the already-open original directory outside the DSH home and point the original path back to that same inode; `linkSync` can then publish the complete temporary file under its managed filename in the moved original directory before the following identity check fails closed. Callers must exclusively manage the DSH home during materialization. The temporary descriptor always closes. If initial identity acquisition fails, cleanup removes the still-reachable random path without attempting identity-based unlink; after identity acquisition, cleanup checks identity before `unlink`. An unreachable random temporary file may remain in a moved original directory, and the identity check plus `unlink` is not an atomic compare-and-unlink against same-permission replacement. Public activation diagnostics redact schemeless `user:pass@host:port` userinfo for DNS names and bracketed IPv6 literals without hiding ordinary `@` text.

The `curated-policy` and `curated-profiles` invariant companions register explained empty installers. Their fixed catalogs and templates have no event-stream or mutable-data relationship; policy plugin loading, focused package tests, and `verify-curated-activation-evidence` retain the static validation.

The [curated benchmark evidence directory](../../../../packages/curated/curated-bench/evidence/README.md) owns activation records and their result artifacts. Every record and referenced artifact is a unique repository-owned tracked stage-zero regular blob there; each JSON record follows the operation schema and binds its separate result artifact by SHA-256. Package-authored, ignored, and untracked files cannot authorize activation.

The allowlist records each candidate by stable id, capability, canonical credential-free GitHub repository URL, full commit SHA, package metadata, license, bundle patch, network and credential assertions, install lifecycle scripts, target profiles, active flag, warnings, blockers, and eight bounded score dimensions whose sum is the admission score. The policy derives `active`, `qualified`, `pending`, or `rejected` instead of storing another status field: active candidates win first, candidates with complete install metadata and artifact digests whose blockers only name missing activation evidence are qualified, long-cycle or baseline-promotion blockers are pending, and all other blockers are rejected. Every inactive candidate has at least one blocker, so inactive fallback intent cannot exist only in prose. Every reachable source records `sourceContentSha256`. `pnpm run audit-curated-candidates -- --candidate <id>` fetches the fixed commit into a temporary bare Git repository without a checkout. The digest starts with `dsh-source-content-v1\0`, globally sorts entries by UTF-8 POSIX relative path bytes, and hashes length-prefixed entry mode, object type, path, and blob bytes. Symlinks contribute their `120000` mode and link-target blob without being followed; unsupported modes and non-blob entries reject. This identifies the pinned Git tree independently of GitHub's changeable source-archive encoding. A candidate may additionally pin an exact npm version and registry integrity while retaining the audited repository and commit. Every active candidate pins the SHA-256 of its audited installed tree and of its complete runtime dependency lock closure. The installed-tree digest uses its own sorted path-and-content encoding, so the verifier rejects added, removed, or modified direct-candidate files. The closure digest sorts package identities paired with exact registry SRI or immutable Git identity. pnpm v9 aliases resolve through their real target package and snapshot records, and their identities bind both the declaration alias and real target; ordinary dependency identities retain the same representation. An active Git dependency cannot declare `preinstall`, `install`, `postinstall`, `prepare`, or `prepack`; it must use a verified prebuilt npm artifact or remain inactive. Catalog-only validation checks these declarations for consistency; it does not fetch or prove upstream artifacts. For a materialized profile, observed lock verification, preflight, and smoke derive provenance from the profile dependency spec, root pnpm lockfile, and pnpm's installed lock snapshot. Git candidates must agree with the catalog repository, commit, path, package version, and tree digest; npm candidates must agree with the exact version, integrity, and tree digest. Ordinary peer suffixes remain valid, while root/workspace `overrides`, `patch_hash` suffixes, `patchedDependencies`, `packageExtensions`, and pnpmfile transformations reject because rewritten dependency content has no independent catalog pin. Both lockfiles must describe the same complete runtime closure reachable through `dependencies` and `optionalDependencies`: every registry dependency has an exact version and SRI, every direct Git locator exactly matches its resolved repository, full commit, and package path, and every GitHub tarball is commit-addressed. Both computed closure digests must also match the catalog, so matching attacker edits to both lockfiles still reject. pnpm verifies registry archive integrity during installation. Observed admission validates this dependency lock provenance and detects direct candidate-tree tampering; it does not claim to detect an attacker who rewrites arbitrary transitive dependency files without changing either lock. The commands require each canonical selected package root to remain under the profile's canonical `node_modules` root and canonicalize every manifest, bundle-patch, and main path before access. Windows drive, UNC, backslash, traversal, symlink, and junction escapes fail on every host. Files use no-follow opens where supported and `fstat()` before and after bounded descriptor reads, then recheck the opened identity against its package-relative path and regular ancestors; non-regular files, replaced paths or ancestors, files that change during the read, files over 16 MiB, and direct-candidate trees over 64 MiB fail. The commands then validate the installed manifest, bundle patch, declared main file, dependencies, lifecycle hooks, Node range, and candidate-specific safe settings without running package scripts. Candidate bundle patches use the Loader's `entryListSchema`; malformed mapping rows fail at every inserted and grouped level. After Cordis composition, every effective top-level and nested group row must carry non-empty string `id` and `name` fields, and each truthy group must contain an entry-list `config`, before candidate entry IDs are compared with the catalog. Observed preflight composes candidate, profile, Harness-home, and explicit overlay patches. Every plugin and group row must retain ownership from an approved selected catalog candidate or an installation-owned shipped bundle, regardless of `disabled`; Cordis imports a group even when its literal `disabled` value is true. User-controlled profile, home, and explicit overlay patches reject `!!js` before Loader parsing, including name, config, and `disabled` overrides of approved rows; approved catalog and installation bundle patches retain their audited expressions. Permission providers remain stricter: their row and every ancestor group must omit `disabled` or set it to literal `false`. Static config overrides of approved plugin rows remain valid when they preserve ID and module name, while user-controlled plugin and group insertions fail closed. Preflight applies conflict, resource, and secret checks to the same recursive entry set. Missing, floating, stale, malformed, transformed, or mismatched package-manager state fails closed. An explicit artifact root without a managed profile is metadata-only and never establishes observed success; package-authored sidecars are not admission evidence. Smoke performs observed artifact and package-manager staging in a terminable worker, then invokes the shipped CLI's `--dump-config` and `--help` stages under one execution-work deadline. Every worker result, error, or timeout releases its timer, listeners, and event-loop reference before termination starts, and the command awaits worker exit before returning. Worker construction and termination cleanup are non-preemptable overhead outside the work budget, so the command makes no hard total wall-clock claim. Production observed smoke copies the validated profile and optional Harness-home patch into a private execution home, revalidates that copy, and starts both CLI stages from it, so later mutation of the supplied live path cannot change child inputs. Smoke does not import candidate modules or synthesize bundle shims. Metadata and config secret checks cover curated fields; malformed-YAML diagnostics retain the parser location, caret, and non-secret code-frame lines without attaching the parser exception that retains the original source, while escape-aware key parsing redacts complete secret scalar continuations. Non-JSON diagnostics remove the complete remainder of a physical line after a secret-shaped assignment key, including every Authorization scheme and multiword value, while preserving the key and preceding non-secret context. Smoke subprocesses remove names containing `KEY`, `PASSWORD`, `SECRET`, `TOKEN`, `AUTH`, `CREDENTIAL`, or `COOKIE`, case-insensitively, after ambient and explicit environments are combined; proxy URLs with userinfo are also removed, every returned output stream redacts URL userinfo, and a timed-out detached process tree receives TERM then KILL before the runner awaits quiescence and deletes its temporary directory. A candidate with inaccessible source, unclear license, missing package metadata, missing bundle patch, incompatible Node metadata, core-patch requirements, unresolved safety controls or threat-model requirements, or another hard rejection remains inactive and does not enter an active profile template. Inactive fallback candidates may stay in the allowlist when their audit record explains why only one provider owns a capability in a profile.

The materialized profile patch is empty while no third-party candidate is active. Candidate-specific safety settings remain in the catalog for later admission. Every curated profile writes `ignore-scripts=true`, generated workspaces contain no build grant or package transformation, and existing unsafe files reject before any write. Observed verification of an exact generated curated manifest requires `private: true`, its generated dependency-name set without additional dependency sections, and both root and installed pnpm lockfiles even when that set is empty. The CLI also forces pnpm's script-suppression configuration and environment for every plugin-management operation. Preflight scans each raw profile, Harness-home, and explicit overlay patch for secrets before composition, including target-only patches that composition discards. Preflight parses config-only overrides but does not compare them with an official `--dump-config` baseline, so an operator reviews replacement-field completeness. `verify-lock` reports catalog metadata and selected observed artifacts as separate counts with an explicit provenance scope. Benchmark schema 3 comparisons require identical task-and-attempt sets, critical flags, environments, DSH build identities, and measurement identities, at least five repetitions per task, finite overflow-safe aggregate means, raw-value threshold decisions, and digest-verified embedded lock and profile snapshots. The build identity records DSH package version, full source revision, source-tree digest, dirty state, executable digest, and Node version; the measurement identity records the producer, tokenizer, prompt/schema serialization, timing, pricing, and scoring implementations. Each lock or profile reference contains a safe relative JSON path from the benchmark fixture directory and the snapshot's canonical JSON SHA-256. Its canonical path stays inside that directory, its regular-file read is bounded, and its digest must match before semantic validation. The referenced baseline content must canonically equal the embedded snapshots, and every profile snapshot must exactly match its authoritative shipped or curated template before rollback data is returned. Completed JSON output retains the content-addressed references and execution identities. The comparator returns the decision, reasons, and immutable rollback content; an external rollout operator performs restoration, without an automatic or atomic restore claim. Planned records without runs may omit execution identities. `evidenceKind: observed`, producer metadata, and run fields remain operator-trusted assertions: neither the label nor an `accepted` result cryptographically authenticates their producer or evidence. E3/E4, A/B, fault, and canary evidence remains pending.

Rollback lock snapshots encode each candidate as shared artifact identities plus one install source. Registry sources carry an exact npm version and SHA-512 SRI; Git sources carry a normalized HTTPS repository, full commit, explicit repository path, and an empty lifecycle-script record. Static validation enumerates every published JSON file in the lock and profile directories, requires schema version 2, a directory-matched kind, a non-empty profile, and the complete payload, and applies exact install-source validation to every lock candidate. Snapshot file reads open the contained canonical target and require its nonzero device/inode identity to match the opened descriptor and post-open path checks before and after reading. Empty candidate arrays remain valid for first-party baselines.

Planning metadata that cannot reconstruct a schema 2 lock or profile lives under `baselines/history` as recursively validated schema 1 `curated-planning-history` records with `evidenceKind: planned` and `restorable: false`. Each record preserves its former lock/profile paths, kinds, operator instructions, counts, catalog reference, and profile bundles in a migration map. The comparator accepts only schema 2 rollback snapshots, so history remains available without becoming restoration input.

Benchmark runs require `failure: null` on success and a non-empty failure reason otherwise. Failure distributions count every failed run through a `Map`, including property-like names, and expose keys in locale order.

The smoke execution-work budget starts at the function entry. JavaScript cannot preempt synchronous `Worker` construction; the command charges its elapsed time when construction returns and fails immediately if the budget is exhausted. Worker inspection and child stages remain terminable. The production child runner receives the remaining budget and the public command awaits its process-tree and temporary-directory cleanup; an injected runner is a trusted test control that must honor the supplied timeout and settle only after its own cleanup. Every outcome clears timers and listeners before awaiting termination. Captured stdout and stderr share a 1 MiB limit, whose overflow follows the timeout termination path and returns a bounded diagnostic. Proxy filtering recognizes conventional and npm-config names case-insensitively, removes URL values with userinfo, and preserves non-URL bypass lists. Constructor overrun and termination cleanup may extend total wall-clock duration; callers that require a hard operating-system deadline supervise the CLI process.

## Alternatives considered

**Put curated behavior in `agent-loop` or another core package.** Rejected because curated admission is composition policy. The core loop already receives a fully assembled plugin tree and does not need third-party source, license, install-script, or profile-tier rules.

**Extend the shipped `web` and `headless` templates directly.** Rejected because curated profiles are opt-in compositions. The official templates remain stable baselines, while curated templates can carry higher supply-chain and profile-specific risk without changing existing launch behavior.

**Run third-party install or build scripts during audit.** Rejected because install lifecycle code is exactly one of the facts being evaluated. The repository records the scripts and validates metadata without executing them; profile installation remains an explicit package-manager operation outside curated admission checks.

**Install LoongSuite from its pinned Git commit.** Rejected because the Git artifact declares `prepack: pnpm run build`. Exact npm `0.1.1` contains the compiled entry and matching bundle patch, has no install-time script, and its release tag points to the pinned commit, so every curated profile uses that artifact without a build grant.

**Trust a package-authored provenance sidecar.** Rejected because a modified package can copy the expected repository, commit, and source-content fields into its own sidecar. Managed profiles use pnpm's normal lock state, and every observed path compares the installed bytes with the independently maintained catalog tree digest.

**Run the full observed preflight during every boot.** Rejected because `curated-scripts` depends on the CLI and profile packages, so importing it from the launcher would create a release cycle and make startup perform artifact-tree and lockfile inspection. The profile package owns a small mandatory composition admission; observed preflight remains the explicit deeper artifact and lock verification.

**Keep failed candidates in active profiles as disabled placeholders.** Rejected because a runnable profile must not depend on a candidate whose audit failed. Rejections remain visible in the allowlist, but the active profile path contains only accepted providers for its scenario.

**Vendor or fork third-party plugins into this repository.** Rejected because the curated layer is a governance and composition layer, not a source mirror. Full source adoption would make this repository responsible for every candidate's build, tests, and dependency updates.

**Keep the curated packages private or bundle them into the CLI.** Rejected because the published CLI resolves bundle and profile packages by npm identity at runtime. A private workspace-only dependency leaves the installed CLI's dependency graph unresolved, while bundling it would replace the established dynamic package-loading model and would not publish the user-facing curated commands.

## Consequences

Curated profile files are reproducible from checked-in declarations and deterministic templates, while existing `web` and `headless` users keep the same composition until they choose a curated profile. A DSH release packs all five curated packages and verifies their exported files and installed dependency graph before publication. Reproducible files do not establish third-party installability or runtime behavior. The model sees no governance text from the curated packages themselves; model-visible prompt sections, tools, or results appear only from bundles that a profile actually loads.

The audit snapshot is intentionally conservative. A candidate can be useful and still remain inactive when the current evidence is insufficient. External installation and initialization, Chrome browser regression, real search, memory, browser, and MCP A/B workloads, real-candidate fault injection, and 3–7 day canary evidence remain pending and cannot be replaced by fixtures or planned records.

No active Agent Note is archived by this decision. The profile-bundle note still owns bundle resolution and launcher behavior, and the repository-plugin removal note still owns the decision to avoid a second external-plugin distribution path.
