# Agent Note: 工作流运行拥有取消权

Status: implemented

[English](2026-08-26-workflow-single-cancellation-owner.md) | 中文

## 问题

同步工作流启动曾通过 `WorkflowStartRequest.signal` 和返回的 `WorkflowRun.cancel()` 同时公开取消能力。工作流与 Ralph 消费方既把同一个调用方信号传入请求，也添加调用运行句柄的监听器，因此一次中止会通过两条路径进入 worker host。host 只为协调这些重复路径而维护输入信号监听器状态。

移除请求信号后，仍需处理一次添加监听器时的竞态。调用方信号可能在同步 `start()` 期间或消费方添加监听器时中止。添加监听器后立即检查状态可以封闭该竞态，但如果转发本身不具备幂等性，两次观察都可能调用回调。

## 决策

`WorkflowStartRequest` 只包含启动数据。`WorkflowEngine.start()` 同步返回，返回的 `WorkflowRun` 是唯一的运行时取消权威。

每个消费方按相同顺序负责自己的调用方信号：在 `start()` 前拒绝已经中止的调用；运行返回后，添加一条有守卫的监听器，最多把一次中止转发给 `run.cancel()`；立即复查信号；然后在 `finally` 中移除监听器并等待 `run.dispose()`。守卫会在调用 `run.cancel()` 前取得所有权，因此同步重入无法再次转发取消。

`WorkflowRun.cancel()` 保持幂等并保留第一个原因。worker host 的 `AbortController` 是该方法向待处理及已发布子 agent 扇出的内部机制，不是另一条公开取消通道。dispose 会汇入同一套运行自有的取消与清理状态，限制 worker 结算与终止时间，并在所有宿主侧提供方启动和子 agent dispose 达到完全停稳后返回。

工作流元数据、运行 id、进度叙述、生命周期事件、持久记录以及 agent start/end 配对保持不变。

## 测试

工作流与 Ralph 消费方测试覆盖预先中止的调用、同步启动期间中止、运行中中止、结算后中止、添加监听器时重入、最多一次转发、移除监听器和 dispose 时完全停稳。worker-thread 测试覆盖立即取消、运行中的子 agent、重入取消时第一个原因优先、最多一次发送 worker 取消、强制结算与完全停稳的 dispose。构建后 worker 测试以及无密钥工作流／Ralph 快照会执行装配后的产物，预期输出保持不变。

## 取代关系审计

本决策只部分取代已拒绝的[工作流收缩提案](../../rejected/simplification/2026-07-12-collapse-workflow-to-foreground-core.zh.md)中的取消部分。该 Note 保持活跃并与本文互链，因为它提出移除工作流元数据、进度事件、运行身份和生命周期配对的更广泛方案；这些内容仍是有意义的被拒绝替代方案。

已实现的[动态工作流](../feature/2026-07-05-dynamic-workflows.zh.md)和 [Ralph 工作流工具](../feature/2026-07-19-fresh-agent-ralph-workflow-tool.zh.md) Note 保持活跃，因为它们分别负责能力与策略依据；其取消说明链接到本文。没有其他活跃 Agent Note 负责工作流重复取消通道，本次限定范围的审计不归档或删除任何 Note。

## 考虑过的替代方案

**保留请求信号作为防御性后备。** 拒绝，因为 `start()` 会同步发布句柄。消费方无需为引擎提供第二条公开路径，就能覆盖启动前及添加监听器时的中止；重复路径会使原因仲裁与监听器释放更难验证。

**让 `start()` 变为异步。** 拒绝，因为引擎会同步完成请求校验和句柄发布。引入异步就绪阶段只会扩宽服务约定，以保留一条没有所有权区间的取消通道。

**共享跨包桥接辅助函数。** 拒绝，因为每个消费方只需围绕自己的 `exec.signal` 使用一段本地守卫回调；新增导出的工具函数会扩展 API，却不能消除有意义的复杂性。

## 后果

引擎只有一个公开取消操作，不再有调用方信号监听器生命周期。消费方保留一条小型显式桥接，并且必须维持预检查、添加监听器、立即复查、移除监听器和 dispose 的顺序。重复或重入的中止观察只会产生一次 `run.cancel()` 调用，而运行本身继续负责第一个原因仲裁、worker 终止、子 agent 取消与完全停稳。
