# 00 · 背景与目标

对应飞书蓝本 §1（调研范围、口径与关键结论）与 §9（最终建议）。

## 1. 背景与调研口径

- 候选全集：Awesome DeepSeek Harness 中文清单，20 个主分类、630 条记录、620 个唯一 GitHub 仓库。
- 核验方式：第一轮抓公开仓库星标/归档/提交规模；第二轮对 46 个重点候选做浅克隆，核验最新提交、`package.json`、`dsh.bundle.patch`、Node 版本、许可证、测试文件、CI 工作流与已知限制。
- 快照日期：2026-08-24。星标只用于发现候选，**不作为准入依据**；大型父仓库星标 ≠ 子插件成熟度。
- 运行环境：DSH 处于 developer preview，蓝本记录根包版本 `0.1.1-rc.2`，要求 Node.js `^22.19.0 || >=24.0.0`。

> 深度调研补充〔2026-08-25 §二〕的实测进一步佐证"星标不作准入依据"：640 条目 / 629 唯一仓库中，星数中位数为 3、仅 5.1% 达 100 星，96% 仓库创建于 2026-08（生态年龄约 12 天）；55 个链接（8.6%，全属 `dsh-external` 组织）已 404，该组织的统一 catalog 数据源本身亦已失效。任何以清单为输入的自动化流程必须先做链接存活校验。

## 2. 关键结论（决定整份计划的形状）

1. 不构建"全家桶"，而是建立可锁版本、可回滚、按能力域互斥的**精选插件层**；`web-curated` 的目标基线固定为 12 个候选，其余进入场景包或实验池。
2. 同一能力域最多保留一个默认 provider；第二个只能作为显式 fallback，不能同时向 `ctx`、工具注册表或 UI slot 注册同名能力。
3. 安全执行顺序固定：**核心沙箱约束 → 确定性 permission-rules → 高风险人工审批或 AI 复核 → 工具执行 → 结果审计**；AI 只处理规则无法静态编码的灰区，超时、解析失败或模型不可用时 fail-closed，不能替代规则引擎或沙箱。
4. 冲突最高的五类：记忆、上下文压缩、浏览器、搜索、远程运行时，必须互斥 profile 或能力开关。
5. UI 美化、趣味插件、IM 通道、领域技能不进通用默认栈，只进独立场景包。
6. **单插件坏 → 整机不启动**（深度调研补充〔2026-08-25 §一/§四〕）：官方 boot 失败以非零码退出并销毁部分上下文，坏插件不是被单独禁用而是拖垮整个 harness。因此集成必须分阶段、每阶段可回滚；证据不足的候选在 allowlist 中保持 inactive，并且不进入可启动模板。
7. **peer/semver 大面积失配**：用真实 semver 库实测，56 个声明 `@deepseek-ai/dsh-*` peer 的插件中 48 个（85.7%）至少一条与 `0.1.1-rc.2` 不匹配（预发布版本默认解析需共享 [major,minor,patch] 且自带预发布标签）。集成须锁定 DSH 版本、对 peer 警告以 `includePrerelease` 语义人工复核、把 DSH 升级视为需全量回归的破坏性事件，**不采信任何第三方兼容徽章**。

## 3. 本计划的落地目标

在**当前 monorepo 内**新增一组 `@deepseek-ai/dsh-*` 包，实现蓝本描述的 `dsh-curated` 精选层：

- **不改核心**：DSH 核心（模型适配器、工具、会话、Agent loop）保持不变，只通过 documented seams 扩展。
- **产出物**：一个内部精选 bundle + 多个 profile + 准入策略文件 + 评测基线 + 校验脚本（详见 [01-目标架构.md](01-目标架构.md)）。
- **遵循仓库既有约定**：新增包严格按 [docs/cookbook/adding-a-package.md](../../cookbook/adding-a-package.md) 的清单创建，bundle/profile 走 [app-boot Profiles](../../../packages/boot/app-boot/README.md#profiles) 契约。

当前实现提供五个可安全物化的 profile，目标基线仍为 12 个候选。`dsh-web-search-pro`、`dsh-memento`、`dsh-mcp-panel`、`dsh-checkpoint-rewind`、`dsh-lsp-actions` 与 LoongSuite OTel 仅为静态/安装资格候选；它们没有真实固定产物的 keyless assembled runnable snapshot，因此全部保持 inactive，runtime active 数为 0。`dsh-web-search-pro` 还缺少必需的 `@anweat/dsh-browser` bundle/runtime dependency。五个 profile 只包含由安装提供的基础 bundle。候选只有在同时提供真实固定产物、keyless assembled snapshot、全部必需依赖 bundle，以及安装、启用、重启、禁用或卸载证据后才能转为 active；E3/E4、A/B 与 canary 状态及完整证据定义见 [06-深度调研复评与证据分级.md](06-深度调研复评与证据分级.md)。

### 3.1 落地形态说明（与蓝本的差异）

蓝本把 `dsh-curated` 描述为一个**独立下游发布单元**（消费 DSH 的外部项目）。本计划按用户决策改为**在当前 monorepo 内新增 packages**，因此：

- 蓝本目录树中的 `dsh-curated/` 根，映射为 monorepo 内的一个新包组 `packages/curated/`（纯容器目录，见 [01-目标架构.md](01-目标架构.md)）。
- bundle 依赖使用 workspace 内部依赖；**第三方外部插件**使用精确版本/SHA 锁。
- 第三方外部插件仍是外部依赖，通过 profile 的 out-of-tree `dependencies` 安装并锁定。

## 4. 既有系统不变量清单（禁止触碰）

> 依据 superpowers 系统演进护栏：向既有系统增能力时，当前行为是契约而非背景。以下不变量在整个执行过程中必须逐项保持不变；实现与 review 必须逐项举证未破坏。

### 4.1 核心运行时不变量

- **Agent loop 语义不变**：不修改 `packages/core/agent-loop`；新能力只挂 documented 扩展点（[docs/architecture.md](../../architecture.md)）。
- **会话日志契约不变**：`SESSION_FORMAT_VERSION` 不因本层变动；任何模型可见输入若新增，必须走既有 session event 机制（"模型可见 ⟺ 可从会话日志重建"）。
- **既有 profile 不被改写**：不直接修改官方 `web`/`headless` profile；精选层是**新增** profile，官方 profile 保持可用。
- **capability seam 完整性**：新增能力若是可替换能力，必须成套提供 Service Definition / Provider / Consumer 三角色，不得只加其一。
- **注册即副作用**：所有贡献走 `ctx.effect()` / `ctx.on()`，registry 的 `register()` 返回 disposer；HMR 卸载可逆。

### 4.2 既有用户路径不变量（回归矩阵锚点）

以下既有用户路径在接入任何插件后必须仍可用，作为 [04-评测体系.md](04-评测体系.md) 回归矩阵的锚点：

- Web 界面启动、URL 打印与浏览器 handoff（[web-app bundle](../../../packages/bundle/web-app/README.md)）。
- headless 一次性任务模式（[headless bundle](../../../packages/bundle/headless/README.md)）。
- 既有工具执行管线（`tools/pre-execute` → 执行 → 结果）语义与顺序。
- 既有权限/审批交互（`packages/interaction`）。
- 既有会话导出/持久化（`packages/session`）。

### 4.3 冲突高发区的强约束

- 记忆、上下文压缩、浏览器、搜索、远程运行时**同域最多一个默认 provider**；第二实现只能显式 fallback。
- 自动压缩、自动记忆、自动继续、自动审批**禁止一次性同时开启**，必须分别评估。

## 5. 全局约束（每个任务隐含包含）

- **不改核心**：任何要求修改 DSH 核心、无 bundle 声明、许可证不清晰、安装脚本越权、Node 版本不匹配的插件一律拒绝。
- **版本锁**：npm 包锁精确版本；GitHub 包锁完整 commit SHA；禁止无约束 `latest`。
- **叶级门禁**：每个验收步骤是一条耗时 < 1 分钟、可独立判定的命令（用户规则第 1、3 条）。
- **规划材料不冒充产品契约**：本目录记录本次本地执行与外部候选 rollout 计划，不进入产品文档网站，也不作为已交付运行时行为的权威来源；已交付行为以源码、包 README、子系统文档与实现类 Agent Note 为准。
- **不擅自 git 操作**：`git add`、commit、push、merge、rebase、reset 需用户显式授权；只读差异检查不受此限制。
- **文档语言**：中文。
- **既有不变量优先**：§4 清单高于任何新增便利。
- **Node/pnpm 版本**：与仓库根一致（`^22.19.0 || >=24.0.0`）。

## 6. 分层成功判据（Definition of Done）

三层完成状态必须独立报告，低层完成不得升级为高层完成。

### 6.1 仓库治理基础设施完成

当前 monorepo 实现完成，当且仅当：

1. 精选层的所有新增包按仓库清单创建，通过适用的 constraints、typecheck、lint、build 和 hygiene 门禁。
2. 五个 profile 可安全物化；未满足激活证据的外部候选不会进入可启动模板。
3. 12 个目标基线候选均有八维静态准入结果；6 个静态/安装资格候选与其余拒绝候选均保留机器可读证据，runtime active 为 0。
4. verify-lock、observed preflight、observed smoke、activation-evidence 与 benchmark comparator 对无效、伪造、错配或不完整输入 fail-closed；fixture 或 synthetic shim 不能生成 observed/active 结论。
5. 动态比较器只接受相同任务/attempt 集与环境、每任务至少重复 5 次的输入，以未舍入值判定阈值，并只引用经过摘要校验的 rollback lock/profile 快照。

### 6.2 单个候选激活完成

某个候选只有同时满足以下条件，才可从 inactive 进入目标 profile：真实固定产物及来源摘要、完整 runtime 依赖 bundle、keyless assembled runnable snapshot，以及该候选在每个目标 profile 中的安装、启用、重启、禁用或卸载证据。其 observed preflight 与 observed smoke 必须基于调用方提供的真实已安装 profile 和解析产物通过，不能以 fixture 或 synthetic shim 替代。一个候选激活完成不代表同域 A/B 或 rollout 完成。

### 6.3 生态 rollout 完成

[03](03-实施路线图.md) 的 P1/P2 只有在对应外部实验实际执行后完成：搜索、记忆、浏览器、MCP 的真实用户路径与 A/B，真实故障注入，以及 3–7 天、至少 100 个真实任务的 canary/灰度记录。当前这些项目均为 pending；仓库治理基础设施通过不得被表述为整份 rollout 路线图完成。

> 注：本仓库当前**是** DSH 核心本体。若最终选择将精选层作为独立下游项目交付（而非 monorepo 内包），§3.1 的映射需相应调整；此为已在规划阶段确认的落地目标，不在执行期变更。
