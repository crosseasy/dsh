# 04 · 评测体系与择优指标

对应飞书蓝本 §6（评测体系与择优指标）。

评测分两部分：**静态准入**（能否进候选池）与**动态择优**（同类插件谁胜出）。星标只用于发现和社区信号，不能补偿安全、兼容或效果缺陷。

## 1. 静态准入：100 分

| 维度 | 权重 | 测量项 | 硬门槛 |
|---|---|---|---|
| DSH 原生兼容 | 20 | `dsh.bundle.patch`、Node engine、无需改核心、profile 可安装、HMR 可卸载 | 无 bundle 或要求核心补丁直接拒绝 |
| 功能完整性 | 15 | 核心流程覆盖、失败语义、配置项、可观测性、导入导出 | 主流程必须可自动验证 |
| 测试与 CI | 15 | 单测、集成、安装 smoke、跨平台、发布校验 | 默认插件至少有自动测试或可复现 smoke |
| 安全与隐私 | 15 | 最小权限、fail-closed、凭证处理、路径围栏、外发控制、审计 | 存在明文凭证或默认越权直接拒绝 |
| 维护健康 | 10 | 最近提交、发布节奏、issue 响应、破坏性变更说明 | 归档或长期不可构建拒绝 |
| 性能成本 | 10 | 启动耗时、RSS、prompt/schema token、后台任务、外部请求 | 超过 profile 预算不得默认启用 |
| 可运维性 | 10 | 版本锁、升级、备份、回滚、诊断、日志 | 无法单插件禁用或回滚不得默认启用 |
| 社区信号 | 5 | 插件自身星标、fork、用户反馈、采用案例 | 只加分，不做硬门槛 |

### 1.1 评分档位

- ≥85 分 → 进入**默认候选**
- 75–84 分 → 进入**场景候选**
- 65–74 分 → 仅**实验**
- <65 分或命中硬拒绝项 → **不纳入**

父仓库星标最多计 2 分；插件子目录必须独立评估。

### 1.1.1 三层门禁作前置淘汰门

catalog 为全部候选保留并校验八维受限分数，但 [02 §2.1](02-插件矩阵与择优.md) 的三层硬门禁（可激活性 → 接缝正交性 → 可回滚性）实行淘汰制：未声明 `dsh.bundle.patch`、同集群双 provider 或不可锁版本者直接硬拒绝；分数不能补偿硬拒绝，不参与通过候选的准入排序，候选也不得进入 profile。证据分级见 [06 §2](06-深度调研复评与证据分级.md)。

### 1.2 静态准入叶级门禁

静态准入映射到 [03 路线图](03-实施路线图.md) 的脚本门禁，均为秒级命令：

- 八维评分 → catalog 逐维记录受限分值，解析器计算总分并拒绝与声明总分不一致的候选
- DSH 原生兼容 → `verify-lock.mjs --artifact-root <absolute-path>` 检查精确解析产物的 `dsh.bundle.patch`、Node engine、当前 Node 兼容性与 core 修改路径；不提供产物根目录时只产生 metadata-only 结果
- 测试与 CI → 克隆核验测试文件数与 CI 工作流数（记录到 benchmarks 清单）
- 安全与隐私 → preflight 递归扫描完整 Cordis entry（包括未知顶层字段）和 curated metadata 的疑似 secret；benchmark 在字段解析前扫描完整 JSON；两者均对诊断脱敏并允许合法环境变量引用，smoke 子进程使用清理后的环境
- 可运维性 → observed smoke 必须读取真实已安装 profile，校验候选 manifest、bundle patch 与 main 文件存在性，再运行已安装 DSH CLI 的 `--dump-config` 与 `--help`；命令不直接导入或初始化候选模块，也不启动 profile runtime，缺失或非法产物即 fail-closed，且不生成 synthetic shim
- Runtime 启用 → 必须有真实固定产物的 keyless assembled runnable snapshot、全部必需依赖 bundle，以及安装、启用、重启、禁用或卸载证据；静态准入和 observed smoke 均不能替代该条件

## 2. 既有系统回归矩阵（不变量验收）

> 依据 superpowers 系统演进护栏：新功能 smoke 不能替代既有用户路径验收。以下矩阵锚定 [00 §4.2](00-背景与目标.md) 的既有用户路径不变量，每接入一个能力域后必须全绿。

### 2.1 既有用户路径回归矩阵

| 既有路径 | 验收方式 | 叶级门禁命令 | 通过判据 |
|---|---|---|---|
| Web 产物与 CLI 配置面 | observed smoke | `node .../smoke-profile.mjs --profile web-curated --profile-root <absolute-path>` | 真实产物检查、`--dump-config` 与 `--help` 均成功；不表示 runtime 已启动 |
| headless 一次性任务 | keyless assembled snapshot | `pnpm exec vitest run --config vitest.snapshot.config.ts examples/headless-agent/tests/headless.snapshot.ts -t 'runs one task through the product headless profile command' --reporter=dot` | 官方 headless profile 完成一次任务且输出匹配已签入快照 |
| 工具执行管线 | real-composition fixture | curated profile Loader 测试 | `pre-execute`、执行与 side effect 顺序符合预期 |
| 权限/审批交互 | real-composition fixture + observed preflight | curated profile Loader 测试与真实 profile root | 拒绝路径无 side effect；权限插件配置 fail-closed |
| 官方会话持久化与导出 | [JSONL owner 测试](../../../packages/session/session-persistence-jsonl/tests/jsonl.spec.ts) + [会话导出 owner 测试](../../../packages/session-query/session-log-export/tests/archive.host.spec.ts) | `pnpm exec vitest run packages/session/session-persistence-jsonl/tests/jsonl.spec.ts packages/session-query/session-log-export/tests/archive.host.spec.ts --reporter=dot` | JSONL 写入后可逐字读取和重开；官方导出 ZIP 保留根会话原始产物内容 |
| 第三方会话导出候选准入 | catalog 与 profile 模板测试 | curated-policy 与 curated-profiles focused tests | `plugin-session-export` 因子包缺少 `engines.node` 而保持 inactive，且不进入 `web-research`；该事实不替代官方会话路径回归 |

官方 session owner 测试固定现有持久化、原始读取和 Host 导出不变量；第三方 `plugin-session-export` 的 inactive 状态是独立准入事实。上述本地 real-composition fixture 只证明仓库内接线和拒绝路径，不证明第三方插件在真实环境中的长周期行为。外部浏览器、搜索、记忆、MCP、故障和 canary 运行仍须另行取得具体运行证据，`observed` 标签本身不能完成该证明。

### 2.2 Web 回归（CDP 9333，用户规则第 0 条）

侵入 UI 的插件（如 `DSH-better-sidebar`）须做 Web 回归，必须用 Chrome + CDP 端口 9333，禁止 IDE 内置浏览器：

- [ ] 启动后 CDP 连通性：`curl -s http://localhost:9333/json/version | grep -q Browser && echo "cdp ok"`
- [ ] 控制台无 error（有 error 须修复）
- [ ] 既有面板/URL/handoff 未被新面板挤占或改写

## 3. 动态择优：任务效果优先

动态总分构成：

```text
任务成功率 30% + 结果质量 20% + 安全正确性 15% + 可靠性 15%
+ 性能与成本 10% + 操作体验 5% + 升级兼容 5%
```

同类插件在**相同** DSH、模型、prompt、workspace、网络和随机种子下做 A/B；baseline 与 candidate 的 `taskId`/`attempt` 集必须完全一致，每个任务至少重复 5 次，报告均值、P50、P95 和失败分布。阈值使用未舍入原始值判定，展示值的舍入不得改变 accepted、rejected 或 rollback 决策。

### 3.1 非补偿门槛（一票否决，不论总分多高）

- 安全正确性 < 95%
- 数据丢失事件 > 0
- 无法回滚
- 启动失败率 > 1%
- 关键任务成功率下降 > 3 个百分点

## 6. 比较决策与回滚线

`compare-benchmark` 对 `securityCorrectness < 95%`、数据丢失、任一运行不可回滚、启动失败率 >1% 或关键任务成功率下降 >3 个百分点返回 `rejected`。它在以下任一性能或成本条件成立时返回 `rollback`：

- P95 首 token 延迟增加 >15%。
- prompt 与工具 schema token 的平均总量增加 >20%。
- 单任务平均成本增加 >20%，且任务成功率提升 <3 个百分点。

比较结果携带上一版 lock 与 profile 的完整不可变快照和触发原因。每个快照都内嵌完整恢复内容并带规范 JSON 的 SHA-256；摘要不匹配、引用可变 catalog 或缺少必要字段时比较失败。`compare-benchmark` 不改写本地 profile；外部 rollout 操作者负责消费决策并恢复快照。

### 6.1 回滚线叶级门禁

- 启动失败率 → 独立保留的真实 runtime/canary 运行记录；`smoke-profile.mjs` 退出码不计作启动样本
- prompt/schema token 增长 → 外部 benchmark producer 必须使用同一固定版本 tokenizer，分别对实际发送的 system/user/history prompt 内容与实际发送的 tool schema JSON 计数；baseline 与 candidate 的 producer/tokenizer identity 必须完全相同，`--dump-config` 不能产生该指标
- 成本增长 → 使用同一 producer 保留的 provider usage/cost 记录；展示型费用插件只可交叉核对，不能替代原始 benchmark 记录

当前仓库只提供比较器，不提供 prompt/schema tokenizer producer。顶层 benchmark schema 3 要求已完成的 baseline 与 candidate 记录完全一致的 DSH build identity（包版本、源码 revision、源码树摘要、dirty 状态、可执行产物摘要与 Node 版本）以及 measurement identity（producer、tokenizer、prompt/schema 序列化、计时、定价与评分实现）；四个 lock/profile 引用都以 `{ path, sha256 }` 绑定 canonical JSON 内容。未记录这些 identity 的输入不能证明可比性或 token 回滚线，相关长周期评测保持 pending。

## 7. 评测执行落地

评测资产落在 [01 §2.2](01-目标架构.md) 的 `packages/curated/curated-bench/`：

- `manifests/`：每个候选插件的克隆核验清单（测试数、CI 数、许可证、bundle 声明、审计时间）。
- `tasks/`：各能力域任务集（§4）。
- `baselines/`：官方 profile 与精选 profile 的启动指标、A/B 结果、回滚线基准。

比较脚本 `compare-benchmark.mjs`（见 [03 路线图](03-实施路线图.md) 脚本清单）读取 `baselines/`，输出同类插件的均值/P50/P95/失败分布与非补偿门槛判定。

仓库内默认 benchmark 的 `evidenceKind` 为 `planned`，搜索、记忆、浏览器、MCP 与 canary 列在 `pendingCampaigns` 中且运行列表为空。Runtime active 候选数为 0，`web-curated` 的 lock snapshot 不含第三方候选。`planned` 只表示未运行，不能自动满足 E1；`fixture` 只描述输入来源，具体内容充分时可支持 E1/E2，但该标签本身不升级证据。`evidenceKind: observed`、producer metadata 与运行字段都是输入提供者对记录来源的断言；比较器只校验字段结构、任务/attempt 集、环境、重复次数、关键任务和阈值，不证明记录由哪个运行器或操作者生成，也不对 producer 或 evidence 提供密码学认证。`accepted` 只表示这些输入通过可比性与决策检查，不能独立证明 E3/E4。真实 E3/E4 结论还必须独立保留来源信息和对应的安装、启用、重启、禁用或卸载及用户路径运行产物，E5 必须由另一环境独立复现。完整证据定义见 [06](06-深度调研复评与证据分级.md)。
