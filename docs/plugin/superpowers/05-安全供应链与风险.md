# 05 · 安全、供应链与风险

对应飞书蓝本 §4.2（版本与供应链策略）、§4.3（冲突检测）、§4.4（安全与数据边界）、§8（风险与未决项）。

## 1. 版本与供应链策略

- npm 包锁定精确版本；GitHub 包锁定完整 commit SHA，**不允许 branch/tag 漂移**。
- 保存解析后的：规范化源码内容 SHA-256、许可证、依赖树、安装脚本、原始仓库、审计时间。GitHub 明确说明 source archive 的压缩参数可变，因此 catalog 不把 tar/gzip 外层字节摘要作为长期 pin；`pnpm run audit-curated-candidates -- --candidate <id>` 在临时 bare Git 仓库中读取固定 commit 的 object database，不创建 checkout。`sourceContentSha256` 以 `dsh-source-content-v1\0` 开头，按 UTF-8 POSIX 相对路径字节对条目全局排序，再依次哈希带 64 位大端长度前缀的 entry mode、对象类型、路径和 blob 字节；symlink 哈希链接目标 blob 而不跟随目标，非 blob 与不支持的 mode 会被拒绝。
- 安装前由操作者运行适用的来源检查和投毒扫描。当前 curated 命令不编排 `dsh-plugin-check`、`upstream-radar` 或 poison scanner。
- 拒绝以下插件：要求修改 DSH 核心、无 bundle 声明、许可证不清晰、安装脚本越权、Node 版本不匹配。
- 升级采用 canary profile，验证通过后再更新精选 bundle；保留上一个可运行锁文件和 profile 快照。
- 带 `prepare`、`prepack` 等 lifecycle build hook 的 Git 依赖会在安装期执行未受 profile 构建授权完整控制的嵌套构建，因此不得保持 active。候选必须改用与固定源码对应、包含已编译入口与 bundle patch、没有 `preinstall`/`install`/`postinstall` 的确切 npm 产物，否则拒绝。六个静态/安装资格候选保留确切 npm 或 Git 产物、registry integrity、目录与依赖闭包摘要，但在 assembled snapshot 和生命周期证据齐全前保持 inactive；全部五个 profile 写入 `ignore-scripts=true`，CLI 也强制 pnpm 的禁用脚本配置，workspace 不生成构建授权。
- 企业场景排除无许可证与 AGPL 项（深度调研补充实测：56 个仓库未声明许可证；OpenViking 为 AGPL-3.0 有传染风险）。

### 1.1 供应链门禁映射

由 [03 路线图](03-实施路线图.md) 的 `verify-lock.mjs` 落地（叶级）：

- 校验精确版本/完整 SHA，拒绝无约束 `latest`。
- 无 `--artifact-root` 时只校验 catalog 元数据并报告 `observed:false`。受管 profile 根从 profile manifest、根 `pnpm-lock.yaml`、已安装 `node_modules/.pnpm/lock.yaml` 快照和已安装包派生来源，并比对仓库、commit、子包路径、包版本、许可证、依赖树、安装脚本、bundle patch 与 main 文件。不含 `dsh.profile` 的独立产物根同样只产生 metadata-only、`observed:false` 结果；包内 `.dsh-curated-artifact.json` 不能建立 observed success，也不能覆盖受管 profile 状态。
- 受管精选 profile 拒绝 `patchedDependencies`、`packageExtensions`、pnpmfile hook 和 lockfile `patch_hash` locator；没有独立 catalog patch 内容 pin 的变换后代码不能通过来源校验。普通 peer suffix 不受影响。
- 每个 active 候选固定 `runtimeDependencyClosureSha256`。校验器从 root lock 与 installed lock 分别遍历 `dependencies` 和 `optionalDependencies`，按 package identity 与确切 registry SRI 或不可变 Git identity 排序计算摘要；两份摘要必须彼此一致并匹配 catalog，因此攻击者同步改写两份 lock 的传递版本或 SRI 仍会被拒绝。
- 每个目标 profile 的 activation evidence 绑定当前模板、全部 active 候选、安装来源、配置覆盖、源码、目录与 closure identity 的 canonical 摘要；证据文件必须是 Git tracked 普通 blob，并通过 no-follow、有界 descriptor 与前后 `fstat` 读取。Repository doc gate 与 DSH release gate 会重放每个 candidate/profile/operation 的精确 keyless snapshot 测试，任意命令或手写成功 JSON 不能授权激活。
- 精选 bare install 会移除 ambient npm/pnpm config，只使用 profile `.npmrc` 与本地 pnpm store，并在已有 profile lockfile 时强制 frozen lock；本地缺少预取产物时安装失败，不回退到网络。调用 pnpm 前还会拒绝 workspace/lock/modules/store 根重定向、包变换与构建授权。Profile 与 `profiles` 根必须是 DSH home 内普通 canonical 目录，symlink 与 junction 逃逸会在写入前拒绝。
- 核对产物声明的 Node engine 与当前 Node 版本，并拒绝修改 `packages/core` 的产物。
- 标记越权安装脚本（`postinstall` 触网/写系统路径）。

## 2. 冲突检测（Preflight 必查项）

Observed preflight 要求绝对 `--profile-root`，解析 profile manifest、每个真实已安装 bundle manifest/patch 与 profile patch；无法解析任一产物时 fail-closed。Fixture 只用于非观测静态校验，不能返回 accepted。Preflight 至少检查：

1. 重复 entry ID、同一 `ctx` service 的多 provider、重复工具名、重复命令名。
2. 多个插件同时监听 `agent/pre-step`、`agent/request`、`tools/pre-execute` 时的声明顺序与 `next()` claim；preflight 校验 catalog 中的 `<event>:next` 声明，真实 `next()` 委托由候选激活前的 keyless assembled runtime observation 证明（waterfall 语义，见 [docs/cordis-primer.md](../../cordis-primer.md)）。
3. UI slot、Settings tab、路由、端口、SQLite 文件、缓存目录和环境变量冲突。
4. 记忆自动注入、上下文压缩、搜索抓取、浏览器控制产生的重复 token 和重复外部请求；静态 resource claim 只能提示风险，候选激活证据必须记录 assembled 运行中两类重复计数均为 0。
5. config-only patch 是否完整重述原配置：**DSH patch 替换整段 config，遗漏字段会静默改变行为**。当前由操作者对照官方 `--dump-config` 审查，preflight 不自动判断字段完整性。

### 2.1 冲突检测门禁映射

由 [03 路线图](03-实施路线图.md) 的 `preflight.mjs` 落地（叶级）：

- 同域双 provider → 以 `capability-conflicts.yaml`（[02 §4](02-插件矩阵与择优.md)）中的 default provider、fallback 与 rule 为权威关系，拒绝同域多 active provider、能力名不一致和策略外 provider。
- 重复工具名/命令名/entry ID → 扫描全量 patch/manifest。
- patch 完整性 → 操作者对照官方 `--dump-config` 基线审查被替换段；当前 preflight 没有 official-dump 输入或自动完整性比较。

## 3. 安全与数据边界

- 插件默认只获得完成任务所需的**最小**工具、路径和网络域名。
- 凭证只引用环境变量或 DSH credentials service（[credentials-local](../../../packages/credentials/credentials-local/README.md)），**不写入** profile、日志和会话导出。
- 搜索、浏览器、IM、Office、远程运行时的域名 allowlist、上传限制、正文脱敏和审计留存期属于部署要求；当前 curated profile 不提供通用网络执行机制。
- OTel 默认仅采集 span、耗时、token 和错误码；prompt、completion、文件内容和工具参数**默认关闭**。
- 配置导入必须 dry-run、分区批准，并拒绝 sessions 和任意文件写入；可用 `dsh-config-manager` 的审批导入思路实现。

Catalog 保留候选启用时必需的安全配置：`dsh-memento` 使用 `writePolicy: ask`、空 `writePolicies` 与 `proposals.enabled: false`；LoongSuite 使用 `captureContent: false`。当前没有第三方 active 候选，profile patch 为空。`dsh-permission-rules` 的 npm `0.5.5` bundle patch 未设置 `enforce: true`，因此保持 inactive；精选层不会依赖后续 profile override 掩盖产物默认值。

`dsh-config-manager` 的固定产物没有 profile 级 dry-run 或执行确认字段，因此当前被拒绝且不进入任何 active profile。Preflight 会递归扫描完整 Cordis entry（包括未知顶层字段）和 curated metadata，benchmark 会在字段解析前扫描完整 JSON；二者均拒绝疑似 secret、允许合法环境变量引用，且诊断不回显原值。Smoke 子进程从清理后的父进程环境启动，只恢复允许的非秘密变量。

### 3.1 安全执行顺序（固定）

```text
核心沙箱 → permission-rules → 高风险人工审批/auto-review → 工具执行 → 结果审计
```

任何 LLM 超时、解析失败或模型不可用都 **fail-closed**（拒绝而非放行）。核心沙箱先建立执行约束，确定性规则在执行前判定，AI 审查只补充灰区；**LLM 审批不能替代规则引擎或沙箱**。

### 3.2 数据边界叶级门禁

- 凭证不落盘 → 会话导出/日志 grep 无凭证明文
- OTel 正文关闭 → LoongSuite profile 配置检查 `captureContent: false`；权限策略种子保留 `otelCaptureBody: false`，通用嵌套配置检查只在实际字段名为 `captureBody` 时拒绝 `true`
- 配置导入 dry-run → 仅当候选具有可由 profile 强制的 dry-run 或执行确认配置时才允许激活；当前 `dsh-config-manager` 不满足

## 4. 风险与未决项

对应飞书蓝本 §8。以下为规划期已识别、执行期须持续跟踪的风险：

| 风险 | 说明 | 应对 |
|---|---|---|
| DSH 快速迭代 | 第三方插件在 `0.1.0-rc.x` 通过 ≠ 在 `0.1.1-rc.2` 可用 | 以实际安装 smoke 为准，每次 DSH 升级重跑 P0 出口判据 |
| 父仓库 ≠ 可激活 bundle | 部分高星项目是父仓库/客户端/运行时/技能/子目录适配器，非 `dsh plugin add` 可直接激活 | 集成目录显式标注类型（插件/客户端/运行时/技能/子目录适配器） |
| 高采用项目测试不足 | `dsh-plugin-hub`、`dsh-cost-meter` 等测试覆盖不足 | 不仅凭星标进生产默认栈，补外部验收 |
| 自动化行为闭环漂移 | 自动压缩/自动记忆/自动继续/自动审批改变 Agent 行为闭环 | 分别评估，**禁止一次性同时开启**（[00 §4.3](00-背景与目标.md)） |
| 外部系统数据合规 | IM、浏览器、Office、远程运行时涉及外部系统与用户数据 | 部署方补充数据分类、保留期、地域、审计与授权策略 |
| peer 大面积失配 | 实测 85.7%（48/56）声明 peer 与 `0.1.1-rc.2` 不匹配 | 锁 DSH 版本；升级走全量回归；`includePrerelease` 人工复核；不采信第三方徽章 |
| 单插件坏 → 整机不启动 | 官方 boot 失败非零退出并销毁上下文 | 分阶段装；每阶段保留完整 baseline lock/profile；失败时恢复上一版完整 lock/profile，并从 active profile/dependencies 移除失败候选。`disabled: true` 仅用于诊断，不能作为最终 runnable 状态 |
| `agent-presets.roots` 被静默覆盖 | Discussion #403，master 未修，真实层序多一层启动器注入 | 不依赖自定义 preset roots；改用 `includeUserRoot` |

E3/E4、搜索、记忆、浏览器、MCP、真实故障注入、A/B 与 canary 均为 pending。计划资产和 fixture 只固定输入、门槛与失败语义，不构成运行完成证据；完整启用条件见 [06](06-深度调研复评与证据分级.md)。

### 4.1 未决项（需部署方/用户决策）

- 若最终改为**独立下游项目**交付而非 monorepo 内包，[01 §2.2](01-目标架构.md) 的映射需相应调整（本次规划已确认落地为 monorepo 内新增 packages）。
- 企业 profile 的域名 allowlist、上传限制、审计留存期的具体值由部署方给定。
- `dsh-feishu` 等外部通道的威胁建模结论决定其是否从实验档升入场景档。

## 5. 与仓库既有安全约定的一致性

本层的安全策略与仓库既有约定对齐（不新增、不覆盖）：

- 权限/审批走既有 [interaction](../../../packages/interaction) 能力，不另起炉灶。
- 沙箱走既有 `ctx.sandbox` seam（[docs/architecture.md](../../architecture.md)）。
- 凭证走既有 [credentials](../../../packages/credentials/credentials-local/README.md) service。
- 防御式模式遵循 [docs/defensive-patterns.md](../../defensive-patterns.md)。
