# 05 · 安全、供应链与风险

对应飞书蓝本 §4.2（版本与供应链策略）、§4.3（冲突检测）、§4.4（安全与数据边界）、§8（风险与未决项）。

## 1. 版本与供应链策略

- npm 包锁定精确版本；GitHub 包锁定完整 commit SHA，**不允许 branch/tag 漂移**。
- 保存解析后的：tarball SHA-256、许可证、依赖树、安装脚本、原始仓库、审计时间。
- 安装前运行 `dsh-plugin-check` 和 `upstream-radar`。
- 拒绝以下插件：要求修改 DSH 核心、无 bundle 声明、许可证不清晰、安装脚本越权、Node 版本不匹配。
- 升级采用 canary profile，验证通过后再更新精选 bundle；保留上一个可运行锁文件和 profile 快照。

### 1.1 供应链门禁映射

由 [03 路线图](03-实施路线图.md) 的 `verify-lock.mjs` 落地（叶级）：

- 校验精确版本/完整 SHA，拒绝无约束 `latest`。
- 无 `--artifact-root` 时只校验 catalog 元数据；提供真实已安装工件根目录后，解析 `.dsh-curated-artifact.json`、package manifest 与 bundle patch，并比对仓库、commit、tarball SHA-256、许可证、依赖树和安装脚本。
- 核对工件声明的 Node engine 与当前 Node 版本，并拒绝修改 `packages/core` 的工件。
- 标记越权安装脚本（`postinstall` 触网/写系统路径）。

## 2. 冲突检测（Preflight 必查项）

Observed preflight 要求绝对 `--profile-root`，解析 profile manifest、每个真实已安装 bundle manifest/patch 与 profile patch；无法解析任一工件时 fail-closed。Fixture 只用于非观测静态校验，不能返回 accepted。Preflight 至少检查：

1. 重复 entry ID、同一 `ctx` service 的多 provider、重复工具名、重复命令名。
2. 多个插件同时监听 `agent/pre-step`、`agent/request`、`tools/pre-execute` 时的顺序和 `next()` 调用（waterfall 语义，见 [docs/cordis-primer.md](../../cordis-primer.md)）。
3. UI slot、Settings tab、路由、端口、SQLite 文件、缓存目录和环境变量冲突。
4. 记忆自动注入、上下文压缩、搜索抓取、浏览器控制产生的重复 token 和重复外部请求。
5. patch 是否完整重述原配置：**DSH patch 替换整段 config，遗漏字段会静默改变行为**。

### 2.1 冲突检测门禁映射

由 [03 路线图](03-实施路线图.md) 的 `preflight.mjs` 落地（叶级）：

- 同域双 provider → 以 `capability-conflicts.yaml`（[02 §4](02-插件矩阵与择优.md)）中的 default provider、fallback 与 rule 为权威关系，拒绝同域多 active provider、能力名不一致和策略外 provider。
- 重复工具名/命令名/entry ID → 扫描全量 patch/manifest。
- patch 完整性 → 与官方 `--dump-config` 基线 diff，检测被替换段是否遗漏字段。

## 3. 安全与数据边界

- 插件默认只获得完成任务所需的**最小**工具、路径和网络域名。
- 凭证只引用环境变量或 DSH credentials service（[credentials-local](../../../packages/credentials/credentials-local/README.md)），**不写入** profile、日志和会话导出。
- 搜索、浏览器、IM、Office、远程运行时分别配置：域名 allowlist、上传限制、正文脱敏、审计留存期。
- OTel 默认仅采集 span、耗时、token 和错误码；prompt、completion、文件内容和工具参数**默认关闭**。
- 配置导入必须 dry-run、分区批准，并拒绝 sessions 和任意文件写入；可用 `dsh-config-manager` 的审批导入思路实现。

当前 profile 明确写入并由 preflight 检查三组安全配置：`dsh-memento` 使用 `writePolicy: ask`、空 `writePolicies` 与 `proposals.enabled: false`；`dsh-permission-rules` 使用 `badFilePolicy: fail` 与 `enforce: true`；LoongSuite 使用 `captureContent: false`。Observed 工件校验还会核对权限插件自身 bundle patch 中的 fail-closed 配置，实际权限决定委托给该插件执行。

`dsh-config-manager` 的固定工件没有 profile 级 dry-run 或执行确认字段，因此当前被拒绝且不进入任何 active profile。命令会扫描普通配置和 curated metadata 中的疑似 secret，诊断不回显原值；smoke 子进程从清理后的父进程环境启动，只恢复允许的非秘密变量。

### 3.1 安全执行顺序（固定）

```text
核心沙箱 → permission-rules → 高风险人工审批/auto-review → 工具执行 → 结果审计
```

任何 LLM 超时、解析失败或模型不可用都 **fail-closed**（拒绝而非放行）。确定性规则先行，AI 审查只补充灰区，沙箱兜底——**LLM 审批不能替代规则引擎**。

### 3.2 数据边界叶级门禁

- 凭证不落盘 → 会话导出/日志 grep 无凭证明文
- OTel 正文关闭 → 检查 OTel 配置默认 `captureBody: false`
- 配置导入 dry-run → 仅当候选具有可由 profile 强制的 dry-run 或执行确认配置时才允许激活；当前 `dsh-config-manager` 不满足

## 4. 风险与未决项

对应飞书蓝本 §8。以下为规划期已识别、执行期须持续跟踪的风险：

| 风险 | 说明 | 应对 |
|---|---|---|
| DSH 快速迭代 | 第三方插件在 `0.1.0-rc.x` 通过 ≠ 在 `0.1.1-rc.2` 可用 | 以实际安装 smoke 为准，每次 DSH 升级重跑 P0 出口判据 |
| 父仓库 ≠ 可激活 bundle | 部分高星项目是父仓库/客户端/运行时/技能/子目录适配器，非 `dsh plugin add` 可直接激活 | 集成目录显式标注类型（插件/客户端/运行时/技能/子目录适配器） |
| 高采用项目测试不足 | `dsh-plugin-hub`、`dsh-cost-meter` 等测试覆盖不足 | 不仅凭星标进生产默认栈，补外部验收 |
| 自动化行为闭环漂移 | 自动压缩/自动记忆/自动继续/自动审批改变 Agent 行为闭环 | 分别评估，**禁止一次性同时开启**（[00 §4.3](00-背景与目标.md)） |
| 外部系统数据合规 | IM、浏览器、Office、远程运行时涉及外部系统与用户数据 | 部署方补充数据分类、保留期、地域、审计与授权策略 |

搜索、记忆、浏览器、MCP、真实故障注入与 canary 的长周期运行仍为 pending。计划资产和 fixture 只固定输入、门槛与失败语义，不构成运行完成证据。

### 4.1 未决项（需部署方/用户决策）

- 若最终改为**独立下游项目**交付而非 monorepo 内包，[01 §2.2](01-目标架构.md) 的映射需相应调整（本次规划已确认落地为 monorepo 内新增 packages）。
- 企业 profile 的域名 allowlist、上传限制、审计留存期的具体值由部署方给定。
- `dsh-feishu` 等外部通道的威胁建模结论决定其是否从实验档升入场景档。

## 5. 与仓库既有安全约定的一致性

本层的安全策略与仓库既有约定对齐（不新增、不覆盖）：

- 权限/审批走既有 [interaction](../../../packages/interaction) 能力，不另起炉灶。
- 沙箱走既有 `ctx.sandbox` seam（[docs/architecture.md](../../architecture.md)）。
- 凭证走既有 [credentials](../../../packages/credentials/credentials-local/README.md) service。
- 防御式模式遵循 [docs/defensive-patterns.md](../../defensive-patterns.md)。
