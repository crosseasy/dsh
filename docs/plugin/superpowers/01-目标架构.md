# 01 · 目标架构

对应飞书蓝本 §4（集成目标架构）。落地目标：当前 monorepo 内新增 packages，不改核心。

## 1. 架构原则

集成层**不修改 DSH 核心**，而是产出一个内部精选 bundle 和多个 profile。扩展只走 documented seams：`ctx.tools`、`ctx.llm`、`ctx.subagents`、`ctx.sandbox`、`session/event`、`tools/pre-execute` 等（见 [docs/architecture.md](../../architecture.md) 与 [docs/capability-seams.md](../../capability-seams.md)）。这保证插件卸载可逆、HMR 正确释放注册资源。

## 2. 蓝本目录树 → monorepo 映射

蓝本给出的独立发布单元 `dsh-curated/`，映射为 monorepo 内新增包组 `packages/curated/`（纯容器，无 `package.json`、无源码，包统一在其下一级）。

### 2.1 蓝本原始目录（供对照）

```text
dsh-curated/
├── package.json                    # 内部 bundle；锁定所有插件精确版本
├── cordis.patch.yml                # 只负责组合和默认配置
├── profiles/
│   ├── web-curated/                # 通用默认栈
│   ├── web-coding/                 # LSP、rewind、浏览器、子 Agent
│   ├── web-research/               # 搜索、记忆、Office、报告
│   ├── web-enterprise/             # OTel、权限、供应链监控、禁外发
│   └── web-personal/               # 主题、桌宠、通知
├── policy/
│   ├── plugin-allowlist.yaml
│   ├── capability-conflicts.yaml
│   └── permission-rules.yaml
├── benchmarks/
│   ├── manifests/
│   ├── tasks/
│   └── baselines/
└── scripts/
    ├── preflight.mjs
    ├── verify-lock.mjs
    ├── smoke-profile.mjs
    └── compare-benchmark.mjs
```

### 2.2 monorepo 落地映射

| 蓝本条目 | monorepo 落地位置 | 说明 |
|---|---|---|
| `dsh-curated/package.json` + `cordis.patch.yml` | `packages/curated/curated-base/`（bundle 包，声明 `dsh.bundle.patch`） | 精选基线 bundle，只负责组合与默认配置 |
| `profiles/web-*` | `packages/curated/curated-profiles/`（携带 profile 模板与 bundle 组合清单） | 每个 profile 一个有序 bundle 层组合，遵循 [app-boot Profiles](../../../packages/boot/app-boot/README.md#profiles) |
| `policy/*.yaml` | `packages/curated/curated-policy/`（策略文件 + 加载/校验 Consumer） | allowlist、能力冲突表、权限规则 |
| `benchmarks/*` | `packages/curated/curated-bench/`（任务集、清单、基线） | 评测资产与基线，见 [04](04-评测体系.md) |
| `scripts/*.mjs` | `packages/curated/curated-scripts/` 或仓库 `scripts/curated-*.ts` | preflight/verify-lock/smoke-profile/compare-benchmark 门禁脚本 |

> 每个新增包严格按 [docs/cookbook/adding-a-package.md](../../cookbook/adding-a-package.md) 创建：`package.json`（`publishConfig.access: "public"`、`type: module`、cordis 双依赖）、`tsconfig.json`、`src/index.ts`、`README.md`、`src/invariant.ts`。五个 curated 包均属于 DSH 发布族；`curated-policy` 与 `curated-bench` 先于 `curated-base`，`curated-policy` 先于 `curated-profiles`，`curated-base` 与 `curated-profiles` 先于 `dsh`，`curated-scripts` 后于其运行时依赖。新包组 `curated` 需在 `tsconfig.base.json` 的 `@deepseek-ai/dsh-*` 通配加 `./packages/curated/*/src` 候选。

### 2.3 包拓扑与命名

按仓库"命名存在的角色"规则（[adding-a-package.md §3](../../cookbook/adding-a-package.md)）：

| 包 | 角色词 | ctx key | 理由 |
|---|---|---|---|
| `curated-base` | Bundle（patch 层） | 无（仅 patch） | 与 `bundle/base` 同型，只组合不注册服务 |
| `curated-profiles` | Bundle 组合 | 无（仅 profile 模板） | 提供 profile 模板与有序 bundle 层清单 |
| `curated-policy` | Policy | 单数 `curatedPolicy` | 决定允许/选择/限制，不执行机制 |
| `curated-bench` | Directory | `curatedBench` | 暴露任务集与基线，不执行 A/B 工作负载 |
| `curated-scripts` | 门禁脚本 | 无 | 校验型 CLI，无服务 |

## 3. Profile 分层

对应蓝本 §4.1。每个 profile 是一组有序 bundle 层，官方 `dsh-base` 最先应用。

### 3.1 `web-curated`（通用默认基线）

目标基线包含以下 12 个低冲突、高收益候选：

- `dsh-toolkit`（确定性工具）
- `dsh-web-search-pro`（网页搜索/抓取，默认 `ctx.web` provider）
- `dsh-context`（上下文观测）
- `dsh-memento`（有界可审计记忆）
- `dsh-mcp-panel`（MCP 管理）
- `dsh-smooth-stream`（流式输出体验）
- `dsh-checkpoint-rewind`（变更前检查点）
- `dsh-lsp-actions`（LSP 诊断/重构）
- `dsh-permission-rules`（确定性 allow/deny/ask）
- `upstream-radar`（依赖与兼容性监控）
- LoongSuite OTel（可观测性导出）
- `dsh-config-manager`（配置备份/迁移/审批导入）

**不进基线**：多 Agent、浏览器、Office、完整 IM、自动继续、自动进化记忆。

当前有 6/12 个静态/安装资格候选：`dsh-web-search-pro`、`dsh-memento`、`dsh-mcp-panel`、`dsh-checkpoint-rewind`、`dsh-lsp-actions` 与 LoongSuite OTel。它们没有真实固定产物的 keyless assembled runnable snapshot，均保持 inactive 且不进入模板；`dsh-web-search-pro` 还缺少必需的 `@anweat/dsh-browser` bundle/runtime dependency。其余目标候选保留各自的产物、兼容性或安全拒绝。完整启用条件与证据等级见 [06](06-深度调研复评与证据分级.md)。

### 3.2 `web-coding`

目标是在基线上增加 `dsh-agent-team-gui` **或** `dsh-background-agents`（二选一主编排器）、`dsh-computer-use` 与 `DSH-better-sidebar`。这些场景候选尚未通过所需证据，因此当前模板只包含安装自有基础 bundle。

约束：同一 profile 最多启用一种主编排器；后台 Agent 必须设置最大并发、最大委托深度、单任务 token 与超时预算。

### 3.3 `web-research`

当前模板只包含安装自有基础 bundle。`plugin-session-export` 的子包 manifest 未声明 `engines.node`，因此与 `dsh-univer-office`、`dsh-mneme` 和 `dsh-vision-router` 一样保持 inactive，不会进入物化结果。

### 3.4 `web-enterprise`

当前模板只包含安装自有基础 bundle。全部五个精选 profile 都写入 `ignore-scripts=true`，workspace 不生成构建授权或包变换；已有文件若启用脚本、授予构建权限或配置依赖变换，物化会在任何写入前失败。匿名视觉 fallback、外部 IM 正文与未批准浏览器下载对应的候选均未激活。

### 3.5 `web-personal`

当前模板只包含 `dsh-base`、`dsh-web-app` 和 `dsh-curated-base` 三个由安装提供的壳层 bundle，不含第三方候选。主题、桌宠与通知仍是规划方向，并与工程、企业和评测基线**物理隔离**。

### 3.6 Profile 分层对照表

| Profile | 基线 | 新增能力 | 关键开关 |
|---|---|---|---|
| `web-curated` | 安装自有基础 bundle | 目标 12 个；runtime active 为 0 | `ignore-scripts=true` |
| `web-coding` | 安装自有基础 bundle | 主编排器、浏览器、侧栏待评测 | `ignore-scripts=true`；并发/深度/预算上限 |
| `web-research` | 安装自有基础 bundle | 会话导出、Office、mneme、vision 属于后续阶段 | `ignore-scripts=true`；不启用自动巩固或匿名视觉 fallback |
| `web-enterprise` | 安装自有基础 bundle | 当前无第三方候选 | `ignore-scripts=true` |
| `web-personal` | — | 当前无第三方候选 | `ignore-scripts=true`；与其他 profile 物理隔离 |

## 4. 冲突检测（架构层要求）

对应蓝本 §4.3。Observed preflight 解析调用方提供的已安装 profile、每个真实 bundle manifest/patch 与 profile patch；缺失或无法解析的产物会 fail-closed。显式 fixture 只用于非观测静态校验，不能产生 accepted 结果。检查项详见 [05-安全供应链与风险.md §2](05-安全供应链与风险.md)。架构层要点：

- `capability-conflicts.yaml` 是 provider/fallback 关系的权威策略；同域多 active provider、策略外 provider、同一 `ctx` service 多 provider、重复工具名/命令名/entry ID → 拒绝。
- 多插件监听 `agent/pre-step`、`agent/request`、`tools/pre-execute` 时的顺序与 `next()` 调用必须显式（waterfall 语义，见 [docs/cordis-primer.md](../../cordis-primer.md)）。
- config-only patch 必须由操作者对照官方 `--dump-config` 审查字段完整性：DSH patch 替换整段 config，遗漏字段会静默改变行为。当前 preflight 不执行官方 dump 差异比较。
- **home 层级 patch 优先级高于 profile 层**（反直觉，深度调研补充〔2026-08-25 §四.1〕）：官方层叠顺序为"各 bundle → profile 的 `cordis.patch.yml` → home 层 → `--patch` overlay"，机器本地偏好被每个 profile 共享，因此胜过 per-profile 层。覆盖含 `!!js` 的行需重述全部保留字段，否则 `port: !!js ctx.webStartup.port ?? 3080` 被替换为字面量会让 `--port` 静默失效。
- **真实层序比文档多一层启动器注入**：`agent-presets.roots` 存在已确认未修复的缺陷（Discussion #403）——启动器在 `--patch` 之后追加 overlay，把用户配置的 roots 整体替换为出厂 root，而 `--dump-config` 仍显示用户配置，造成"配置已生效"的假象。精选层不依赖自定义 preset roots，改用 `includeUserRoot`。

## 5. 数据流与卸载可逆性

- `dsh` 启动与 `--dump-config` 在 Loader 激活前对五个精选 profile 执行强制 boot admission：manifest bundle 必须与模板及 catalog 分配精确同序，包管理器状态必须安全，profile/home/overlay 只能静态覆盖已批准行。`!!js` 和未批准 plugin/group 插入会被拒绝。该轻量检查由 `curated-profiles` 提供，因此不会形成 CLI 与 `curated-scripts` 的发布依赖环；observed preflight 继续负责产物目录、direct tree 与 lockfile 深检。
- 每个插件的注册走 `ctx.effect()`，返回 disposer；profile 卸载或 HMR reload 必须完全释放（工具名、服务键、UI slot、SQLite 文件、缓存目录、端口、环境变量）。
- 精选 bundle 的 patch 只做组合与默认配置，不携带业务逻辑；业务逻辑在被组合的插件内。
- profile 切换即 provider 切换：降级由配置切换完成，**不**同时暴露两组高度重叠工具（见 [02-插件矩阵与择优.md §3.2](02-插件矩阵与择优.md)）。
- 物化器只为实际 active 候选写入其安全配置；当前没有第三方候选，因此 profile patch 为空。`dsh-memento`、LoongSuite 与 `dsh-permission-rules` 的配置要求仍保留在 catalog，待满足 [06](06-深度调研复评与证据分级.md) 的启用条件后生效。
