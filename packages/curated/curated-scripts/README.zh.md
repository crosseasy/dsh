# `@deepseek-ai/dsh-curated-scripts`

[English](README.md) | 中文

`@deepseek-ai/dsh-curated-scripts` 持有精选插件准入与 profile 证据的源树命令实现。该包导出可测试的命令函数，并为 `verify-lock`、`preflight`、`smoke-profile` 和 `compare-benchmark` 分别交付明确的可执行入口；四个入口共用一个 runner。

## 命令

- `verify-lock` 静态校验 catalog metadata，包括计算得到的八维评分和必需的 Node/core-patch 声明。绝对 `--artifact-root` 只有同时包含受管 `dsh.profile` manifest 与两份 pnpm lockfile 时才会产生 observed 证据；不受管根目录仍只校验 metadata。受管校验会在不执行包脚本的前提下核对来源、catalog 所有的直接候选目录摘要与运行时依赖闭包摘要、manifest、patch、声明的 main 文件、依赖、安装 hook、Node 兼容性和核心路径改动。JSON 报告分别给出 `catalogCandidateCount` 与 `selectedCandidateCount`，并标明 `provenanceScope`，因此不含第三方依赖的 profile 会报告选中 0 个产物，而不会把完整 catalog 表述为已观测。
- `preflight` 接受显式 fixture 进行非观测静态校验，或接受绝对 `--profile-root` 进行观测校验。观测校验会拒绝配置包变换的全部受管 profile，并拒绝启用生命周期脚本或授予构建权限的精选模板。安装自有 bundle 的 manifest 与 patch 只能从当前运行 dsh 安装的 canonical anchor 解析；catalog 候选从受管 profile 解析。Preflight 随后组合 profile patch、Harness home patch 与每个绝对 `--patch` overlay。每个组合后的插件或 group 行都必须由已批准的所选 catalog 候选或安装自带 bundle 持有，无论其 `disabled` 值为何；Cordis 即使看到字面量 `disabled: true` 也会导入 group 行。用户控制的 profile、home 与 overlay patch 会在 Loader 解析前拒绝 `!!js`，包括对 name、config 和 `disabled` 的覆盖；已批准 catalog 和安装 bundle patch 可保留经过 audit 的表达式。用户控制层可以在保留 ID 与模块名称时对已有行应用静态覆盖，但不能插入插件或 group。Preflight 还会执行权威 provider/fallback 策略、重复注册、memento/permission-rules/LoongSuite 安全设置、数据处理默认值，以及对每个完整 Cordis entry（包括未知顶层字段）和 curated metadata 的递归 secret 拒绝；`*Env` 字段中的环境变量引用仍然合法。Profile 组合完成后，有效 `permission-rules` 行及其祖先 group 必须通过省略 `disabled` 或将其设为字面量 `false` 来保持无条件启用；被禁用或有条件启用的 provider 不提供权威 active 声明。权限执行仍委托给解析到的权限插件。
- `smoke-profile` 的观测 CLI smoke 要求绝对 `--profile-root`。它在可终止 worker 中检查 manifest、产物目录、路径、包 metadata、bundle 和 lock，其中 descriptor 读取会对照已打开 identity 复核文件路径与 package 祖先，然后使用显式启动 allowlist 运行 `--dump-config` 与 `--help`。Child 只接收 `PATH`、home/profile、临时目录、Windows launcher、locale、无凭证 proxy、显式 `DSH_HOME` 和显式 `DSH_TELEMETRY_DISABLED` 变量；Node、动态加载器、Python、Ruby 及其它 bootstrap 变量不会从父进程继承。Production observed staging 还会把通过校验的 profile 与可选 Harness-home patch 复制到私有 execution home，并在任一 child 运行前重新校验该副本，因此随后对所提供 live profile 路径的写入无法改变 child 输入。在 POSIX 上，每个 child 使用全新、空白且权限为 0700 的工作目录，只在其 detached process group 全部退出后删除该目录；child 会选择私有 execution home 及其 `node_modules`，内部启动 guard 则阻止 child 加载工作目录或 Harness home 中的 `.env`。Proxy 识别覆盖大小写不敏感的 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY` 及对应 `npm_config_*` 名称。普通 proxy 值只有在它是无凭证、无 query、无 fragment、无非根路径的 HTTP 或 HTTPS origin 时才会保留；`NO_PROXY` 类名称只接受经过校验的非 URL bypass 列表。非法 URL、非法 userinfo 和无 scheme 凭据都会被移除，返回的 stdout 与 stderr 也会遮蔽这些凭据形式。JSON 与文本输出都会按顺序报告带单调时钟 duration 的 `staging`、`manifest`、`bundle-parse`、`dump-config` 和 `help` stage；`staging` 从 worker 构造前开始，到 settle 并等待 termination 后结束，`manifest` 与 `bundle-parse` 则只覆盖各自的同步检查。Stdout 与 stderr 共享 1 MiB 捕获上限。输出超限时，命令会沿用 timeout 的 TERM-to-KILL process-group 清理，再返回有界诊断。完整脱敏后的 JSON 或文本报告在序列化后另受 1 MiB 限制；超限报告会替换为固定的 `smoke-profile-output-limit` 失败，保留有界 stage 摘要，并省略原始错误和 profile 文本。顶层进程以零状态退出但 process group 中仍有运行中的 descendant 时，runner 也会执行清理并返回失败和有界诊断。一个 55 秒执行工作预算从函数入口开始计时。JavaScript 无法抢占同步 `Worker` 构造；构造返回后，命令会重新计算剩余工作预算，预算耗尽时立即失败。Worker 检查和 child stage 可被终止。Production child runner 接收剩余预算，`runSmokeProfile` 会等待 process group 与临时目录清理完成。Worker 返回结果、报错或超时后，命令都会清除计时器与 listener、解除 worker 引用，并等待 worker 终止后再返回。构造与终止清理时间不属于可抢占的工作预算，因此需要硬性总 wall-clock 截止时间的调用方必须在 CLI 进程外监督。缺失、非法或超时的产物会 fail-closed；该命令不会创建 synthetic bundle shim。
- `compare-benchmark` 要求顶层 schema 3，并要求证据显式标为 `observed`、`fixture` 或 `planned`。在字段校验之前，它会递归拒绝完整 parsed input 中任意位置的 secret，包括 execution ID、model/prompt/workspace/network/string seed metadata 与未消费字段；诊断与 observed JSON 均不回显被拒绝的值，`*Env` 环境变量引用仍然合法。已完成的比较必须提供执行 ID 与时间戳，使用完全相同的模型、提示词、workspace、网络与种子值，使用相同的确切 DSH 包版本、源码 revision、源码树摘要、dirty 状态、可执行产物摘要和 Node 版本，并使用完全相同的 producer、tokenizer、prompt/schema 序列化、计时、定价与评分 identity。比较还要求 critical 标记完全一致的任务和 attempt 键、每个任务至少重复 5 次，以及全部必需关键任务。对于有限的运行指标，即使直接求和会溢出，聚合均值仍保持有限。每个内嵌和引用的 lock 或 profile snapshot 都必须声明 `schemaVersion: 2`；缺失版本、旧版本和未来版本均不合法。每个引用只包含安全相对 JSON 路径与该 snapshot canonical JSON 的 SHA-256。每次读取只打开目录内的 canonical target，并在有界普通文件读取前后校验 descriptor/path identity；语义校验前先拒绝过期摘要。Baseline 引用必须与通过摘要校验的内嵌 rollback snapshot 在 canonical JSON 上完全相等；每个引用 profile 还必须按顺序精确等于对应 shipped 或 curated 权威模板。每个 lock candidate 都携带共享 artifact identity 和且仅一个安装来源：确切 SemVer 2.0 npm 版本加 SHA-512 SRI，或 normalized Git repository 加完整 commit、显式 repository path 与无 lifecycle script 事实。合法 prerelease 与 build metadata 可以使用，但不会对 prefix、range 或 tag 进行 coercion。空 lock baseline 合法。对于已完成的 observed 或 fixture 记录，该命令使用未舍入值判断不可补偿阈值，并返回 profile 聚合摘要、决策与原因、按内容寻址的 snapshot 引用、execution identity 与不可变 rollback snapshot 内容，但不会执行恢复。只有声明 pending campaign 且两个 profile 都没有 runs 的 planned 记录才返回 `pending`；它们可以省略 execution identity 与 `requiredCriticalTaskIds`。带 runs 的 planned 记录必须提供已完成记录所需的关键任务声明，会完成比较但保持 unverified；observed 与 fixture 记录不能借 pending campaign 绕过校验或比较。

Observed preflight 会在组合前扫描每个原始 profile、Harness home 与显式 overlay patch 中的 secret 材料，因此 target-only patch 不会先消失再逃过检查。Benchmark run 在成功时必须使用 `failure: null`，失败时必须提供非空原因，从而保证失败分布完整。

Observed verify-lock 将 canonical `profiles/<built-in-curated-name>` 目录视为权威身份，要求 manifest 名称与该目录一致，并要求有序 bundle 列表匹配权威模板。Observed preflight 与 smoke 要求 manifest 名称为 `dsh-profile-<profile>`。对于生成的内置 curated manifest，三个命令都要求 `private: true`、精确的生成 direct dependency 名称集合、不含其它 dependency 区段、即使没有选中第三方候选也同时存在根与已安装 pnpm lockfile、`.npmrc` 精确等于 `ignore-scripts=true\n`，并且 manifest 不含任何 `pnpm` 字段。自定义受管 profile 会解析精确的 `.npmrc` key，拒绝已有的重复或 false `ignore-scripts` 赋值，并继续执行构建授权与包变换逐项检查；为了兼容旧 custom profile，缺少 `.npmrc` 仍然合法。Preflight 只在 canonical root 恰好位于该 home 的 `profiles/<profile>` 时读取 Harness home patch。Production smoke 使用相同的 canonical 布局要求，保证被检查目录就是子进程启动目录；可信的 injected test runner 可以使用其他显式 root。

仓库保留四个 `.mjs` wrapper 作为源树开发入口。npm 包不包含这些文件，只发布四个 built command bin。

## API

仓库 activation verifier 要求 `runtimeActivationEvidence` 的 key 与 `targetProfiles` 精确一致，校验每个 profile 的全部五份记录，并把每份记录的 `profile` 绑定到对应 map key。Evidence 与 artifact 路径必须位于仓库内的普通目录之下；读取使用有界 descriptor，并在前后校验祖先目录和文件 identity。重复 JSON key 会在 `JSON.parse` 前被拒绝，原始 secret-key 扫描也会在解析字段可能隐藏先前值之前执行。Record 与 artifact command 检查会拒绝 scheme URL、option 赋值 URL 和无 scheme `user:pass@host:port` 值中的 URL userinfo，且不回显 argv。

每个 `run*` 函数接收 CLI 风格字符串参数，并返回带 `status`、`stdout` 和 `stderr` 的 `CommandResult`。观测 lock 校验使用 `--artifact-root`；观测 preflight 与 smoke 使用 `--profile-root`，preflight 还接受绝对 `--patch` overlay。带 `dsh.profile` 的根目录具有权威性：`createInstalledArtifactResolver()` 要求每个选定候选项在 `package.json` 中的依赖 spec、根 `pnpm-lock.yaml`、已安装的 `node_modules/.pnpm/lock.yaml` 快照和已安装包与 catalog 中的确切 Git 仓库、commit、路径及包版本，或确切 npm 版本与 registry integrity 保持一致。必需 runtime bundle 必须是同一 profile 中另一个具有完整 activation evidence 的 active 候选；它会作为独立 profile 依赖被选中，并分别满足这四个 observed 位置。Canonical Git 仓库 identity 必须严格采用 `https://github.com/<owner>/<repository>` 形式，不得包含 username、password、port、query、fragment、`.git` 后缀、尾随斜杠、编码路径或其他大小写的 host。Package-manager Git transport 可以在规范化前增加 `git+` 和一个精确的小写 `.git` 后缀；混合大小写后缀会被拒绝。Commit fragment 继续单独解析。Root/workspace `overrides`、`patchedDependencies`、`packageExtensions`、pnpmfile hook 和 `patch_hash` locator 会被拒绝，因为 catalog 没有独立固定被改写的依赖内容；仅含 peer 的 locator 后缀仍然有效。规范化后的选中包根目录必须位于 profile 的规范化 `node_modules` 根目录下。对于通过 pnpm `dependencies` 或 `optionalDependencies` 可达的每个 runtime 依赖，两份 lock 必须包含同一个完整闭包：registry 条目要求确切版本与 SRI，direct Git locator 必须与解析得到的 repository、完整 commit 和 package path 精确一致，GitHub tarball 则必须按 commit 寻址。每份闭包按 package identity 与对应确切 SRI 或 Git identity 排序，并计算 `runtimeDependencyClosureSha256`；两份 lock 的摘要必须彼此相同且匹配候选的 catalog 值。pnpm v9 alias 会通过真实目标的 package 与 snapshot 记录解析，同时每个 alias identity 会绑定声明名称和真实目标 identity；非 alias identity 保持不变。pnpm 会在安装时校验 registry 归档 integrity；observed 准入会校验 lock 来源，并通过 catalog 持有的摘要检测直接候选目录篡改。它不声称能够检测同时不改写两份 lock 而直接改动任意传递依赖文件的攻击者。Catalog 会保留 npm 安装候选的仓库与 commit audit 事实，`sourceContentSha256` 标识该 commit 的规范化文件而不依赖 GitHub 可变的归档编码；registry lock 证明的是版本与 integrity，而不是 Git commit。每个 active 候选还记录 `treeSha256`：校验器会规范化包根目录，以迭代方式按 UTF-8 POSIX 相对路径排序列出包内全部文件，并依次哈希路径长度、路径字节、文件长度与文件字节，因此新增、删除或修改直接候选文件都会让三个观测命令失败。直接候选目录最多包含 1,000 个文件、目录和链接条目以及 64 层嵌套目录。在宿主支持时，文件会以不跟随最终 symlink 的方式打开，在有界 descriptor 读取前后使用 `fstat()` 校验，并对照 package 相对路径与普通祖先重新检查；非普通文件、读取期间发生变化、单文件超过 16 MiB 或使直接候选目录总量超过 64 MiB 都会被拒绝。Manifest、bundle patch 与 main 必须使用可移植的相对路径，而且其真实路径必须位于规范化包根目录内。缺失或不匹配的受管状态会 fail-closed，且不会继续读取包自身的伴随文件或其他产物根。Verify-lock、观测 preflight 和观测 smoke 随后执行同一套 manifest、许可证、依赖并集、生命周期脚本、Node 兼容性、组合包 patch、main 文件和核心路径校验。每个 catalog 候选的 bundle patch 都会使用 Loader 的 `entryListSchema` 解析，并在校验前完成组合。每个插入层级与 group 层级中的非法 mapping 行都会失败。每个顶层有效行和 truthy Cordis group 下的有效行都必须包含非空字符串 `id` 与 `name` 字段，而且每个这样的 group 都必须包含条目列表形式的 `config`；只有满足这些条件后，校验才会将有效 ID 与 `resources.entryIds` 比较。比较时只对两个区分大小写的列表排序，不裁剪或去重，因此额外、缺失、替换与重复 ID 都会失败。Permission-policy 候选还要求有效 `permission-rules` 行及其每个祖先 group 省略 `disabled` 或将其设为字面量 `false`；条件表达式与其他值无法证明权限执行，因此会被拒绝。Observed 所有权、冲突、secret 与有效权限检查会在组合全部输入层后使用相同的递归条目集合。非法 YAML 诊断会保留 parser 原因、已脱敏文件标识、从 1 开始的行列号、caret 和非秘密 code-frame 行；escape-aware 键解析会扫描物理行上的每个 mapping key，并移除完整 secret scalar 与 continuation 行。不完整 JSON 诊断会在序列化前遮蔽带引号的 secret key，包括 `auth`、`auth_*` 和 `*_auth`。非 JSON 诊断会遮蔽 secret-shaped 赋值键后的整条物理行剩余内容，包括任意 Authorization scheme 和多词值，同时保留键及之前的非秘密上下文。Benchmark 输入校验覆盖调用方提供的 `evidenceKind`、执行来源信息和 run 字段。已完成的 observed 与 fixture 比较 JSON 包含执行来源信息、profile 聚合摘要、状态与原因以及不可变 snapshot，不包含原始 run 记录。Planned pending JSON 只包含 `command`、`ok`、`evidenceKind`、`status`、`pendingCampaigns`、`baseline.profile` 和 `candidate.profile`，不包含摘要、决策细节、原因或 snapshot。`observed` 与 `accepted` 决策都不会认证 producer，也不提供密码学证据；这些来源事实仍由 operator 判断是否可信。Fixture benchmark 记录返回 `unverified`，计划中的评测返回 `pending`；两者都不能返回 `accepted`，也不能作为 canary 或故障执行证据。Smoke 默认在包内 worker 中运行生产 observed staging，再解析已安装 `dsh` bin 并用纯 Node 执行。测试可以注入 `SmokeProfileRunner`；显式 profile、artifact-root 和 staging-worker 输入是可信测试控制，不会序列化进生产配置。

## 模型体验

### 离线精选校验

#### 模型看到的内容

这些命令在 agent runtime 之外运行，并向调用方输出文本或 JSON。它们不注册提示词文本、工具 schema、用户消息、助手可见结果或会话事件。

#### Token 影响

`@deepseek-ai/dsh-curated-scripts` 本身没有直接 token 成本。

#### KV Cache 影响

没有直接 cache 影响；只有当调用方显式把命令输出放进另一条提示词时，诊断才会变成模型可见内容。

## 已知限制与暂缓事项

- **不安装第三方包**：这些命令读取调用方提供的已安装产物，但不安装包，也不运行候选安装生命周期脚本。
- **静态结果不是运行时证据**：无 root 的 lock 校验和显式 preflight fixture 会标为非观测；preflight fixture 不会被报告为已通过观测准入，smoke 则要求真实已安装 profile。
- **Windows observed smoke 待实现**：在 Job Object child runner 能证明 descendant quiescence 之前，`smoke-profile` 会在 Windows 上于 spawn `dsh` 前失败。
- **Patch 完整性需要操作者审查**：preflight 会解析并校验已配置字段，但不会把 config-only override 与官方 `--dump-config` 基线比较。
- **仓库不包含长周期运行证据**：默认 benchmark 只列出待执行评测，不伪造运行记录。`compare-benchmark` 会评估输入记录，但不执行外部工作负载、故障评测或 3–7 天 canary。
