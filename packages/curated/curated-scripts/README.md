# `@deepseek-ai/dsh-curated-scripts`

English | [中文](README.zh.md)

`@deepseek-ai/dsh-curated-scripts` owns the source-tree command implementations for curated plugin admission and profile evidence. The package exports testable command functions and ships a distinct executable entry for each of `verify-lock`, `preflight`, `smoke-profile`, and `compare-benchmark`; all four entries use one shared runner.

## Commands

- `verify-lock` validates catalog metadata statically, including the computed eight-dimension score and required Node/core-patch declarations. An absolute `--artifact-root` produces observed evidence only when it contains a managed `dsh.profile` manifest and both pnpm lockfiles; unmanaged roots remain metadata-only. Managed validation checks provenance, the catalog-owned direct-candidate tree digest and runtime dependency closure digest, manifests, patches, declared main files, dependencies, install hooks, Node compatibility, and core-path changes without executing package scripts. JSON reports separate `catalogCandidateCount` from `selectedCandidateCount` and identifies `provenanceScope`, so a profile with no third-party dependencies reports zero selected artifacts instead of presenting the full catalog as observed.
- `preflight` accepts either an explicit fixture for non-observed static validation or an absolute `--profile-root` for observed validation. Observed validation rejects managed profiles that configure package transformations and rejects curated templates that enable lifecycle scripts or grant builds. Installation-owned bundle manifests and patches resolve only from the running dsh installation's canonical anchor; catalog candidates resolve from the managed profile. Preflight then composes the profile patch, the Harness-home patch, and each absolute `--patch` overlay. Every composed plugin or group row requires ownership from an approved selected catalog candidate or an installation-owned shipped bundle, regardless of `disabled`; Cordis imports group rows even when their literal `disabled` value is true. User-controlled profile, home, and overlay patches reject `!!js` before Loader parsing, including name, config, and `disabled` overrides; approved catalog and installation bundle patches retain their audited expressions. User-controlled layers may apply static overrides to owned rows while preserving their ID and module name, but may not insert plugins or groups. Preflight also enforces the authoritative provider/fallback policy, duplicate registrations, memento/permission-rules/LoongSuite safe settings, data-handling defaults, and recursive secret rejection across each complete Cordis entry, including unknown top-level fields, and curated metadata. Environment-variable references in `*Env` fields remain valid. The effective `permission-rules` row and its ancestor groups must remain unconditionally enabled after profile composition by omitting `disabled` or setting it to literal `false`; a disabled or conditional provider contributes no authoritative active claim. Permission execution remains delegated to the resolved permission plugin.
- `smoke-profile` requires an absolute `--profile-root` for observed CLI smoke. It performs manifest, artifact-tree, path, package metadata, bundle, and lock inspection in a terminable worker, with descriptor reads rechecking the file path and package ancestors against the opened identity, then runs `--dump-config` and `--help` with an explicit launch allowlist. The child receives `PATH`, home/profile, temporary-directory, Windows launcher, locale, credential-free proxy, explicit `DSH_HOME`, and explicit `DSH_TELEMETRY_DISABLED` variables; it does not inherit Node, dynamic-loader, Python, Ruby, or other bootstrap variables. Production observed staging also copies the validated profile and optional Harness-home patch into a private execution home and revalidates that copy before either child runs, so later writes to the supplied live profile path cannot change the child inputs. On POSIX, each child uses a fresh empty 0700 working directory that is removed only after its detached process group exits; the child selects the private execution home and its `node_modules`, and an internal launch guard prevents it from loading either working-directory or Harness-home `.env`. Proxy recognition includes case-insensitive `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, and the equivalent `npm_config_*` names. Regular proxy values fail closed unless they are credential-free HTTP or HTTPS origins with no query, fragment, or non-root path; `NO_PROXY`-style names accept only a validated non-URL bypass list. Malformed URLs, malformed userinfo, and scheme-less credentials are omitted, and returned stdout and stderr redact those credential forms. Both JSON and text output report the ordered `staging`, `manifest`, `bundle-parse`, `dump-config`, and `help` stages with monotonic durations; `staging` starts before worker construction and ends after settlement and awaited termination, while `manifest` and `bundle-parse` cover only their synchronous checks. A failed worker result must carry a non-empty issue list or an error; `{ ok: false, issues: [] }` is an invalid protocol result and cannot produce status 0. Stdout and stderr share a 1 MiB capture limit. Output overflow returns a bounded diagnostic after the same TERM-to-KILL process-group cleanup used for timeout. The complete redacted JSON or text report is separately limited to 1 MiB after serialization; an oversized report is replaced by a fixed `smoke-profile-output-limit` failure that keeps bounded stage summaries and omits the original errors and profile text. A top-level zero exit with running process-group descendants also triggers cleanup and returns failure with a bounded diagnostic. One 55-second execution-work budget starts when the function enters. JavaScript cannot preempt synchronous `Worker` construction; after construction returns, the command recomputes the remaining work budget and fails immediately when none remains. Worker inspection and child stages are terminable. The production child runner receives the remaining budget and `runSmokeProfile` awaits its process-group and temporary-directory cleanup. Every worker result, error, or timeout clears its timer and listeners, unreferences the worker, and awaits termination before returning. Constructor and termination cleanup time are outside the preemptable work budget, so callers that require a hard total wall-clock deadline must supervise the CLI process. Missing, invalid, or timed-out artifacts fail closed; the command does not create synthetic bundle shims.
- `compare-benchmark` requires top-level schema 3 and explicit `observed`, `fixture`, or `planned` evidence. Before field validation, it recursively rejects secret material anywhere in the complete parsed input, including execution ids, model/prompt/workspace/network/string-seed metadata and unconsumed fields; diagnostics and observed JSON never echo the rejected value, while `*Env` environment-variable references remain valid. Completed comparisons require execution ids and timestamps, identical model/prompt/workspace/network/seed values, the same exact DSH package version, source revision, source-tree digest, dirty state, executable digest, and Node version, and identical producer, tokenizer, prompt/schema serialization, timing, pricing, and scoring identities. They also require matching task-and-attempt keys with identical critical flags, at least five repetitions per task, and complete required critical tasks. Aggregate means remain finite for finite run metrics, including values whose direct sum would overflow. Every embedded and referenced lock or profile snapshot must declare `schemaVersion: 2`; missing, legacy, and future versions are invalid. Each reference contains exactly a safe relative JSON path and the canonical JSON SHA-256 of that snapshot. Each read opens the contained canonical target, verifies descriptor/path identity before and after the bounded regular-file read, and rejects a stale digest before semantic validation. Baseline references must canonically equal the digest-verified embedded rollback snapshots, and every referenced profile must exactly equal its shipped or curated authoritative template in order. Every lock candidate carries shared artifact identities and exactly one install source: exact SemVer 2.0 npm version plus SHA-512 SRI, or normalized Git repository plus full commit, explicit repository path, and no lifecycle scripts. Valid prerelease and build metadata are accepted without prefix, range, or tag coercion. Empty lock baselines are valid. For completed observed or fixture records, the command evaluates non-compensable thresholds from raw values and returns aggregate profile summaries, a decision and reasons, content-addressed snapshot references, execution identities, and immutable rollback snapshot content without restoring it. Only planned records with declared pending campaigns and no runs in either profile return `pending`; they may omit execution identities and `requiredCriticalTaskIds`. Planned records with runs require the completed-record critical-task declaration and are completed but unverified, while observed and fixture records cannot use pending campaigns to bypass validation or comparison.

Observed preflight scans each raw profile, Harness-home, and explicit overlay patch for secret material before composition, so a target-only patch cannot disappear before inspection. Benchmark runs require `failure: null` on success and a non-empty failure reason otherwise, which keeps failure distributions complete.

Observed verify-lock treats a canonical `profiles/<built-in-curated-name>` directory as authoritative, requires its manifest name to match the directory, and requires its ordered bundle list to match the authoritative template. Observed preflight and smoke require manifest name `dsh-profile-<profile>`. For a generated built-in curated manifest, all three commands require `private: true`, the exact generated direct dependency-name set, no additional dependency sections, both root and installed pnpm lockfiles even when no third-party candidate is selected, `.npmrc` equal to `ignore-scripts=true\n`, and no manifest `pnpm` field. Custom managed profiles require a present `.npmrc` with exactly one effective `ignore-scripts=true` assignment and retain the field-specific build-grant and package-transformation checks. Preflight reads the Harness-home patch only when the canonical root is exactly `profiles/<profile>` under that home. Production smoke applies the same canonical layout requirement so the inspected directory is the directory started by the child process; trusted injected test runners may use another explicit root.

The repository keeps four `.mjs` wrappers for source-tree development. Source execution runs the dsh CLI through tsx with the repository paths map, while built execution runs the manifest-declared dsh bin under plain Node. The npm package omits the wrappers and publishes only the four built command bins.

## API

The repository activation verifier requires `runtimeActivationEvidence` keys to exactly match `targetProfiles`, validates all five records for every profile, and binds each record's `profile` to its map key. Evidence and artifact paths must remain below regular repository directories; reads use bounded descriptors with before-and-after ancestor and file identity checks. Duplicate JSON keys reject before `JSON.parse`, and raw secret-key scanning runs before parsed fields can hide an earlier value. Its record and artifact command checks reject URL userinfo in scheme URLs, option-assigned URLs, and schemeless `user:pass@host:port` values without echoing argv.

Each `run*` function accepts CLI-style string arguments and returns a `CommandResult` with `status`, `stdout`, and `stderr`. Observed lock verification uses `--artifact-root`; observed preflight and smoke use `--profile-root`, while preflight also accepts absolute `--patch` overlays. A root with `dsh.profile` is authoritative: `createInstalledArtifactResolver()` requires every selected candidate's dependency spec in `package.json`, root `pnpm-lock.yaml`, installed `node_modules/.pnpm/lock.yaml` snapshot, and installed package to agree with either the catalog's exact Git repository, commit, path, and package version or its exact npm version and registry integrity. Root and installed direct resolutions must also match, including their peer-suffixed snapshot keys, before their runtime dependency closures are compared. A required runtime bundle must be another active same-profile candidate with complete activation evidence; it is selected as its own profile dependency and must independently satisfy those four observed locations. Canonical Git repository identities use the exact `https://github.com/<owner>/<repository>` form without username, password, port, query, fragment, `.git` suffix, trailing slash, encoded path, or alternate host casing. Package-manager Git transport may add `git+` and one exact lowercase `.git` suffix before normalization; mixed-case suffixes reject. Direct Git locators may also carry ordinary pnpm peer suffixes: the full locator binds the snapshot key, while repository, commit, and package-path validation uses the suffix-free locator. Root/workspace `overrides`, `patchedDependencies`, `packageExtensions`, pnpmfile hooks, and `patch_hash` locators reject because the catalog does not pin rewritten dependency content; peer-only locator suffixes remain valid. The canonical selected package root must remain under the profile's canonical `node_modules` root. For every runtime dependency reachable through pnpm `dependencies` or `optionalDependencies`, both locks must contain the same complete closure: registry entries require an exact version and canonical non-placeholder SRI whose decoded length matches SHA-256, SHA-384, or SHA-512, while direct Git locators must exactly match their resolved repository, full commit, and package path and GitHub tarballs must be commit-addressed. Each closure is reduced to sorted package identities plus those exact SRI or Git identities and hashed as `runtimeDependencyClosureSha256`; both lock digests must match each other and the candidate's catalog value. pnpm v9 aliases resolve through the real target package and snapshot records, while each alias identity binds both the declaration name and real target identity; non-alias identities remain unchanged. pnpm verifies registry archive integrity during installation; observed admission validates that lock provenance and detects tampering in the direct candidate tree through its catalog-owned digest. It does not claim to detect an attacker who can rewrite arbitrary transitive dependency files after installation without changing either lock. The catalog retains repository and commit audit facts for npm-installed candidates, and `sourceContentSha256` identifies the normalized files at that commit instead of GitHub's changeable archive encoding; a registry lock proves version and integrity rather than a Git commit. Every active candidate also records `treeSha256`: verification canonicalizes the package root, iteratively lists every package file by sorted UTF-8 POSIX relative path, and hashes each path length, path bytes, file length, and file bytes. Added, removed, or modified direct-candidate files therefore fail all three observed commands. Direct-candidate trees may contain at most 1,000 file, directory, and link entries and 64 nested directory levels. Files are opened without following the final symlink where the host supports it, checked through `fstat()` before and after bounded descriptor reads, rechecked against their package-relative path and regular ancestors, and rejected when they are non-regular, change during the read, exceed 16 MiB each, or push the direct-candidate tree over 64 MiB. Manifest, bundle-patch, and main paths must be portable relative paths whose real paths stay under the canonical package root. Missing or mismatched managed state fails closed without consulting package-authored sidecars or another artifact root. Verify-lock, observed preflight, and observed smoke then apply the same manifest, license, dependency-union, lifecycle-script, Node-compatibility, bundle-patch, main-file, and core-path validation. Each catalog candidate's bundle patch is parsed with the Loader's `entryListSchema` and composed before validation. Malformed mapping entries fail at every inserted or grouped level. Every effective top-level row and row under a truthy Cordis group must have non-empty string `id` and `name` fields, and each such group must contain an entry-list `config`; only then are effective IDs compared with `resources.entryIds`. The comparison sorts both case-sensitive lists but does not trim or deduplicate them, so extra, missing, substituted, and duplicate IDs fail. A permission-policy candidate also requires its effective `permission-rules` row and every ancestor group to omit `disabled` or set it to literal `false`; conditional and other values reject because they cannot prove enforcement. Observed ownership, conflict, secret, and effective permission checks use the same recursive entry set after composing all supplied layers. Malformed-YAML diagnostics preserve the parser reason, redacted file identity, one-based line and column, caret, and non-secret code-frame lines; escape-aware key parsing scans every mapping key on a physical line and removes complete secret scalar and continuation lines. Incomplete JSON diagnostics redact quoted secret keys, including `auth`, `auth_*`, and `*_auth`, before serialization. Non-JSON diagnostics redact the complete remainder of a physical line after a secret-shaped assignment key, including every Authorization scheme and multiword value, while preserving the key and prior non-secret context. Benchmark input validation covers caller-supplied `evidenceKind`, execution provenance, and run fields. Completed observed and fixture comparison JSON contains execution provenance, aggregate profile summaries, status and reasons, and immutable snapshots; it does not include raw run records. Planned pending JSON contains only `command`, `ok`, `evidenceKind`, `status`, `pendingCampaigns`, `baseline.profile`, and `candidate.profile`; it contains no summaries, decision details, reasons, or snapshots. Failure distributions count every non-empty reason, including property-like names, and sort keys by locale order. Neither `observed` nor an `accepted` decision authenticates the producer or evidence cryptographically; the operator remains responsible for trusting their provenance. Fixture benchmark records return `unverified`, planned campaigns return `pending`, and neither can return `accepted` or serve as canary or fault-execution evidence. Smoke runs observed staging in the package worker, then uses the source-tree or built dsh launch described above. Tests can inject a `SmokeProfileRunner` as a trusted control that must honor `timeoutMs` and resolve only after its own cleanup; explicit profile, artifact-root, and staging-worker inputs are also trusted test controls and are not serialized into production configuration.

For exact managed roots, `createInstalledArtifactResolver()` runs `assertCuratedInstalledLocks()` against the current lock bytes before candidate artifact resolution, including when the selected candidate set is empty. Candidate resolution then performs its artifact checks and consumes a fresh shared policy identity for source and package-version fields. Non-bindable managed roots retain candidate-local manifest and artifact checks; each selected candidate with both lockfiles is admitted by the shared candidate lock validator. Full-profile admission runs when the manifest dependency names exactly match the catalog-selected dependency set.

Runtime closure identities bind a direct candidate's full peer-suffixed snapshot key, each transitive dependency's peer-suffixed resolution key, and the validated package path of each GitHub codeload dependency. Structured `Authorization` and `Proxy-Authorization` tuples and `{ name, value }` records are secret-bearing input; admission rejects them and diagnostics retain the header name while redacting its value. Preflight and smoke retain raw profile names for lookup and execution but redact secret-shaped profile values in text and JSON reports. Production child results and emitted subprocess stages preserve `exitCode`, `signal`, and `timedOut` independently while retaining `status` for compatibility. A staging-worker failure carries exactly one representation: either a non-empty `error`, or a non-empty `issues` array whose `code` and `message` fields are non-empty. The injected monotonic clock observes elapsed worker construction and termination time at its next reading, charges that time against later work and stage duration, but cannot preempt or hard-bound either operation.

## Model Experience

### Offline curated verification

#### What the model sees

The commands run outside the agent runtime and emit text or JSON to their caller. They register no prompt text, tool schema, user message, assistant-visible result, or session event.

#### Token effect

Zero direct token cost from `@deepseek-ai/dsh-curated-scripts`.

#### KV Cache effect

No direct cache effect; diagnostics become model-visible only if a caller explicitly includes command output in another prompt.

## Known Limitations and Deferred Work

- **No third-party installation**: the commands read caller-supplied installed artifacts but do not install packages or run candidate install lifecycle scripts.
- **Static results are not runtime evidence**: rootless lock verification and explicit preflight fixtures are labeled non-observed; preflight fixtures are never accepted as observed profile evidence, and smoke requires a real installed profile.
- **Windows observed smoke is pending**: `smoke-profile` fails before spawning `dsh` on Windows until a Job Object child runner can prove descendant quiescence.
- **Patch completeness requires operator review**: preflight parses and validates configured fields but does not compare config-only overrides with an official `--dump-config` baseline.
- **No long-run evidence is checked in**: the default benchmark lists pending campaigns without fabricated runs. `compare-benchmark` evaluates supplied records but does not execute external workloads, fault campaigns, or 3–7 day canaries.
